# 锁与生命周期

## 1. 选择同步原语

根据执行上下文选择原语，而不是根据接口便利性选择。可睡眠任务路径使用可睡眠锁；中断、调度器和关抢占路径使用中断感知或不可睡眠锁。不能在禁止阻塞的上下文取得可能睡眠的锁，也不能用普通互斥锁掩盖中断重入。

### 1.1 临界区

锁保护的是明确不变量。记录锁内哪些字段必须一致，以及状态何时对外发布。临界区保持狭窄，但不能为了缩短持锁时间而在不完整状态下暂时释放锁。

持有范围较大的锁时避免调用唤醒、通知、设备回调、文件系统、分配器或未知外部实现。无法避免时，必须证明不会反向取得当前锁，也不会观察尚未提交的状态。

### 1.2 加锁顺序

模块拥有多把锁时记录全局顺序，并沿完整调用链检查嵌套取得。不能只验证当前函数；回调、析构、错误转换和日志路径也可能取得其他锁。

需要同时修改多个对象时，优先按稳定键排序后取得，或使用更高层事务边界。依赖重试的尝试加锁必须有界，并明确失败时状态是否仍然可用。

## 2. 等待与唤醒

等待必须在检查条件与进入睡眠之间避免丢失唤醒。典型顺序是：在保护条件的同步边界内检查状态，登记等待者，再释放锁并阻塞；唤醒方先发布状态，再使等待者可运行。

### 2.1 状态优先

唤醒本身不是状态。等待者恢复后重新检查条件，以处理虚假唤醒、多个消费者和状态再次变化。不能用单个任务唤醒替代可观察状态发布，也不能假定唤醒立即在同一处理器执行。

终止、信号、超时和取消与正常完成竞争时，明确哪个结果获胜、其他路径如何观察、谁负责移除等待节点。发布致命状态应先于释放所有停止或等待状态，避免任务再次进入不可唤醒等待。

### 2.2 通知与回调

通知列表、完成回调和唤醒目标需要稳定生命周期。通常先在锁内提取待通知对象或形成快照，再在锁外调用；快照必须继续持有资源，不能留下悬空引用。

重复通知应幂等或被代际状态拒绝。标识符复用时使用代际号或所有权令牌防止陈旧完成作用于新对象。

## 3. 资源生命周期

并发资源需要单一释放责任。队列所有权、直接内存访问缓冲区、中断端点、任务句柄和设备请求应明确从创建、提交、完成、取消到回收的状态机。

### 3.1 部分失败

登记后启用失败、提交后设备拒绝、等待中取消和完成时调用方退出都要有回滚。资源获取即初始化守卫应覆盖每个提前返回；发布给其他执行上下文后，原守卫不能再私自释放。

引用计数只证明对象内存仍在，不自动证明业务状态有效。关闭、卸载或热拔插时还要阻止新操作、等待在途操作结束，并使陈旧句柄得到明确错误。

### 3.2 测试

优先使用可控制的屏障、阶段钩子、模型检查或状态顺序断言构造交错。回归要在错误实现上稳定失败，并验证最终状态、资源计数和所有等待者，而不只验证没有超时。

涉及真实任务调度、中断或跨核通知时，应通过项目 `cargo xtask` 的 ArceOS、StarryOS 或 Axvisor 运行入口取得证据；宿主机伪运行时不能替代真实调度语义。
