# Rust 错误与测试

## 1. 错误边界

错误类型应服务调用方决策。可恢复失败返回 `Result` 或 `Option`，并保留足以转换、重试、回滚或报告的结构化信息；日志不能代替错误传播。

### 1.1 领域错误

库、组件、领域和硬件抽象软件包中的非平凡公共错误枚举使用工作区 `thiserror` 依赖派生 `thiserror::Error`，在 `#[error(...)]` 中提供显示文本。只有体量很小且对依赖高度敏感的软件包才手工实现 `Display` 和 `core::error::Error`。

宿主侧二进制程序和工具软件包使用 `anyhow::Result`、`Context`、`anyhow!` 和 `bail!` 处理顶层编排与面向人的报告。不要把 `anyhow::Error` 泄漏到可复用库接口；在 ArceOS 或内核集成边界把领域错误显式转换为 `ax_errno::{AxError, AxResult}`。

不支持的平台、固件、硬件、客户机、用户内存、文件系统或网络路径返回明确的不支持或领域错误。不得静默采用后备路径、伪造成功、猜测默认值或把结构化元数据改成字符串。

### 1.2 终止与断言

`unwrap`、`expect` 和 `panic` 只用于测试、不可能状态断言、一次性初始化失败或有文档证明的不变量。外部输入、设备状态、资源耗尽、并发竞争和用户请求导致的失败通常可恢复，必须沿调用链返回。

断言用于证明程序内部不变量，不用于校验不可信输入。发布构建不能依赖调试断言维持内存安全、资源记账或用户可见正确性。

## 2. 诊断信息

诊断应说明失败的操作、对象和必要上下文，同时避免输出凭据、用户内存、密钥或无界数据。底层库返回结构化错误，上层在有用户或运维语境时增加路径、设备、目标、参数或阶段信息。

### 2.1 日志层级

正常可预期分支不应刷屏；重试和轮询日志应有界。错误日志不能在多个抽象层重复输出同一根因，除非上层补充了新的决策上下文。

持续集成和运行器必须输出稳定的成功与失败标记，并确保内部失败传播到最外层退出状态。只看到进程退出码为零而没有目标行为的可观察后置条件，不算验证成功。

## 3. 测试策略

测试应位于最接近被保护不变量、同时能够观察真实行为的层级。纯算法可使用单元测试；跨软件包接口使用集成测试；系统调用、内核行为、设备和平台路径使用项目测试套件、QEMU 或实体板卡入口。

### 3.1 确定性回归

修复错误时，先增加在错误实现上必然失败的回归，并记录失败原因；随后实现修复，再让同一测试通过。不得只展示修复后的通过、使用概率性复现、放宽断言、延长超时或删减用例。

回归应直接触发根因。系统调用优先直接调用 `syscall(SYS_...)`；运行器错误要验证发现、选择、执行和失败传播；并发错误要控制交错或验证状态顺序；硬件路径要观察寄存器、队列、完成状态或客户机结果，而不只检查常量。

### 3.2 覆盖边界

至少覆盖正常路径、错误路径、边界值、资源释放和重复调用。新增状态机要覆盖每个可达转换和非法转换；解析器要覆盖截断、溢出、未知字段和不可信长度；所有权修改要覆盖部分构造失败、提前返回和析构。

测试文件存在不等于测试有效。测试应编译真实实现，并通过模块或公共接口观察行为；只有被测试对象本身就是源码文本、生成模板或静态契约，且测试说明理由时，才允许用 `include_str!` 或文本搜索代替执行。必须确认测试能被项目入口发现、构建或安装、选择、执行，并在回归时使最外层任务失败。不能把持续集成覆盖移动到仅手工执行的位置，也不能用跳过掩盖环境或实现缺口。

源文件内的 `#[cfg(test)] mod tests` 放在最后一个 Rust 项目位置，避免测试辅助项打断生产入口和实现顺序。需要大量共享测试基础设施时移入专用测试模块，但不能为方便测试扩大生产公共接口。

## 4. 作者检查

提交前按实际改动检查：

- 入口、状态变化、所有权、失败传播和回滚是否清楚；
- 名称、类型和模块边界是否表达领域概念；
- 可恢复失败是否仍存在 `unwrap`、`expect`、`panic` 或静默回退；
- 新行为和错误修复是否具有正确层级的确定性测试；
- 验证是否使用仓库 `cargo xtask` 入口并覆盖实际目标；
- 注释是否解释不变量而非复述代码；
- 变更是否混入无关重构、重复事实来源或无当前使用者的投机接口；
- 格式化、静态检查、测试输出和可观察后置条件是否已记录。

审查发现问题时给出具体输入、状态、调用链或资源生命周期证据，并说明修复后应恢复的保证。不要只评价风格，也不要因为持续集成绿色而跳过语义、所有权或测试执行链路。
