# Rust 实现与表达

## 1. 代码组织

代码应让维护者从入口快速看出主要流程，再逐步进入细节。文件和模块顶部先放公共入口、核心类型与主要流程，辅助函数和低层细节随后出现；不要为了机械遵守顺序而打散紧密协作的状态机或协议步骤。

### 1.1 单一职责

函数优先完成一次状态转换、硬件操作、系统调用步骤、验证步骤或数据转换。探测、校验、映射、注册、启用和回滚具有不同前置条件或失败处理时，拆成具名阶段。长函数不是单凭行数判定；真正需要拆分的信号是混合多个抽象层、拥有多套错误策略、反复切换状态或难以单独验证。

模块应聚焦一个领域不变量。大型文件可以按状态、协议阶段、所有权或平台适配拆分，但不要创建只转发一个调用且没有独立语义的空壳模块。源文件接近或超过 400 行时主动检查是否混合多个领域；超过约 800 行时应拆分，或在审查材料中说明保持整体的具体不变量和可维护性依据。行数是审查触发线，不是脱离语义的机械失败条件。

### 1.2 修改与副作用

通过 `&mut`、返回值、类型化状态转换或名称清楚的方法显式表达修改。一个函数包含多个布尔控制参数时，优先改为配置结构、枚举或具名入口。读取函数不应暗中注册设备、推进队列、改变凭据或吞掉错误。

资源取得与释放应成对并靠近，能够由所有权和析构表达时使用资源获取即初始化。多阶段操作失败时明确哪些状态已经发布、哪些资源需要回滚，以及调用方能否安全重试。

## 2. 命名与领域词汇

名称应表达领域不变量、单位和所有权，而不是容器形状或临时实现。优先使用地址空间、中断线路、虚拟机、设备、队列、请求、页、页框、能力和错误条件等项目概念。

### 2.1 避免泛化名称

已知更准确概念时，避免使用 `data`、`info`、`mgr`、`handler` 或 `handle`。名称不应只重复类型，例如 `device_vec: Vec<Device>`；应说明集合角色，例如待探测设备、活动队列或已分配中断。

布尔值名称应能直接读出真假含义。单位和坐标系容易混淆时写入名称或使用新类型，例如字节长度、页数、客户机物理地址和宿主虚拟地址不得都以裸 `usize` 传递。

### 2.2 一致性

同一概念在类型、字段、函数、日志和文档中使用同一词。新名称应优先跟随仓库已有的准确词汇；只有旧名称确实表达错误时才在完整调用链内一致迁移，不保留含义相同的双重入口。

## 3. 函数与控制流

正常路径应清晰，边界检查和错误返回靠近其依据。优先使用提前返回减少嵌套；不要把协议步骤压缩成难以审计的链式表达，也不要为了减少行数牺牲错误上下文。

### 3.1 参数与返回值

参数保持最小且关系明确。公共接口出现三个以上相互关联参数时，优先使用配置结构或构建器；多个参数必须共同满足布局、范围或生命周期约束时，用已经校验的结构承载。避免通过可变输出参数返回结果，优先返回结构、元组或迭代器。返回值应让调用方区分成功、暂不可用、不支持和真实失败；不能把具有决策意义的状态折叠成布尔值或日志文本。

迭代器和闭包适合纯转换与局部筛选；协议状态、资源回滚和硬件操作更适合显式控制流。公共接口不要强迫内部创建调用方本可复用的 `String`、`Vec` 或完整克隆；通过借用、迭代器、容量参数或调用方提供的拥有对象让分配责任清楚。热路径避免不必要分配、克隆、格式化和临时集合。

### 3.2 边界条件

检查零长度、空集合、最大值、溢出、对齐、包含与半开区间、部分完成和重复调用。计算地址、大小、页数、队列索引和时间时优先使用受检算术，并在错误类型中保留失败原因。

## 4. 注释与文档

注释解释代码本身不能表达的不变量、安全契约、协议步骤、硬件特殊行为、并发顺序或取舍，不复述语句。公共接口和共享代码的注释使用英文；项目说明文档和协作文本使用中文解释技术逻辑。

### 4.1 公共文档

公共类型和函数说明调用方关心的语义：所有权、单位、失败条件、阻塞性、并发保证、状态变化和兼容性。示例只在能够澄清非显然用法时提供，并确保使用真实公开入口。

`unsafe fn`、`unsafe trait` 以及要求调用方维护安全前置条件的接口必须具有 `# Safety` 契约；具体证明由 `rust-unsafe-safety` 约束。

### 4.2 维护性注释

临时限制必须说明触发条件和可观察后果；有可追踪议题时附议题，不写无上下文的 `TODO`。协议常量、布局规则、错误转换和边界不变量集中维护，避免注释与另一份实现形成竞争事实来源。

## 5. 格式与可读性

仓库固定的工具链和 `rustfmt` 配置是布局事实来源，不在代码评审中发明个人格式规则。提交前运行 `cargo fmt`，不手工对齐会被格式化器改写的内容。

### 5.1 导入与条件编译

导入应让依赖来源清楚，避免大范围通配符掩盖符号归属。条件编译应包围真正的平台或功能边界；不要在函数内部散布大量细碎条件，导致未启用组合缺少类型检查。

### 5.2 代码异味

以下现象要求回到所有权和边界重新判断，而不是立即增加包装层：

- 同一协议常量、错误映射或状态判断在多处复制；
- 调用方穿透多层内部对象才能完成一个领域操作；
- 新增只为一个调用点服务、没有独立不变量的抽象；
- 为绕过类型或生命周期约束进行无依据克隆、泄漏或全局缓存；
- 用字符串传递结构化状态，或用日志代替错误返回；
- 静默回退到猜测的设备、中断、地址、凭据或默认行为；
- 一个修复同时混入无关重命名、格式改写或大范围重构。

删除重复知识不等于机械合并所有相似行。抽象必须让不变量更集中、调用点更容易审计；隐藏关键控制流或迫使调用方猜测状态时，保留局部显式实现更合适。
