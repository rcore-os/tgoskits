# StarryOS 系统调用状态与测试

## 1. 凭据与权限

权限检查使用调用时正确的真实或有效用户、组、能力集合和用户命名空间。不能从宿主、全局变量或初始命名空间读取替代当前任务凭据。

### 1.1 检查与使用

明确权限在哪个对象和命名空间中解释，检查后对象是否可能被替换，以及锁或引用如何防止检查与使用时序竞争。权限成功不能绕过后续参数与对象状态检查，除非 Linux 的实际顺序如此。

凭据修改需要定义线程级或线程组级作用域、继承、复制与写时复制。失败时不能留下半更新的用户标识、组或能力。

## 2. 命名空间与对象状态

进程、挂载、用户、网络和其他命名空间状态必须由正确对象拥有。`clone`、`unshare`、`setns`、`fork` 和 `exec` 对共享、复制、替换和回滚的行为分别追踪。

### 2.1 文件描述符与文件系统

文件描述符表、打开文件描述、路径和文件系统对象具有不同共享层级。复制文件描述符表不能错误复制或合并打开文件描述状态；关闭、偏移、标志和执行时关闭语义按 Linux 对象层级实现。

虚拟文件系统辅助代码改变查找、权限、挂载、符号链接、文件类型或错误传播时，追踪到所有受影响系统调用。不能因为入口文件未改就声明二进制接口不受影响。

### 2.2 进程、信号与会话

进程标识、线程组、父子关系、会话、进程组、停止、退出和等待状态必须有单一所有者。信号发布、可见性、唤醒和状态释放的顺序决定用户可见结果，需同时使用 `rust-concurrency-safety`。

退出、致命信号、跟踪停止和作业控制停止竞争时，先发布能够让所有等待者观察的终态，再释放停止条件。单纯唤醒任务不能弥补状态尚未发布。

## 3. 用户内存

用户指针通过项目用户内存接口访问，检查地址范围、权限、长度溢出、跨页和部分复制。不能把用户地址转成长期 Rust 引用，也不能在持有不可睡眠锁时执行可能缺页的复制。

### 3.1 提交顺序

输入通常先复制并验证，再修改内核状态；输出通常在状态结果确定后复制。若 Linux 允许部分提交，必须精确实现其边界。输出复制失败时，确认内核状态应保留还是回滚，不能凭直觉选择。

## 4. 并发与阻塞

阻塞系统调用明确等待条件、可中断性、超时单位、信号重启和虚假唤醒。等待者恢复后重新检查状态；关闭、取消和对象销毁必须唤醒并返回正确错误。

共享表和对象操作记录锁顺序、引用生命周期和发布关系。原子操作要说明发布者与观察者，`Relaxed` 不能承担权限、对象初始化或终态可见性的同步。

## 5. 系统级回归

系统调用语义回归放在 `test-suit/starryos` 的适当用例或既有分组中，通过精确选择用例的项目入口执行，例如 `cargo xtask starry test qemu ... -c <用例>`。不得只运行无法证明具体用例被选择的汇总入口，也不得只添加宿主单元测试、应用冒烟或标准 C 运行库封装测试。

### 5.1 直接调用

优先使用 `syscall(SYS_...)` 直接传递参数和检查原始返回值与 `errno`，避免标准 C 运行库预处理标志、重试、缓存状态或转换结果。测试覆盖成功、每个关键错误顺序、状态提交、重复调用和清理。

涉及凭据、命名空间、进程、信号或文件描述符共享时，建立多个任务或进程，分别观察共享和隔离结果。只检查当前进程局部变量不能证明内核对象语义。

### 5.2 确定性失败与通过

错误修复的同一测试必须在错误实现上必然失败，在修复后通过。用例输出稳定成功与失败标记，运行器必须发现、构建或安装、选择并执行它，并把内部失败传播到最外层 `cargo xtask` 退出状态。

宿主 Linux 支持同一行为时，使用相同输入运行 Linux 与 StarryOS 并比较返回值、错误码和状态。涉及体系结构二进制接口时，至少覆盖功能声明支持的体系结构，并优先选择系统调用表、结构布局、指针宽度或符号扩展不同的组合。

记录运行体系结构、配置、命令、测试名称、关键输出和可观察后置条件。QEMU 启动成功或测试汇总绿色不能替代具体用例执行证据。

## 6. 审查检查

审查每个受影响系统调用时确认：Linux 版本和源码证据已固定；入口与间接辅助调用链完整；参数、权限、对象和状态检查顺序一致；错误码与部分完成准确；凭据和命名空间所有者正确；用户内存和并发边界安全；直接系统级回归在项目入口真实执行。

任一关键语义只能依赖推测、手册摘要、应用冒烟或修复后成功时，不能据此认定兼容性完成。
