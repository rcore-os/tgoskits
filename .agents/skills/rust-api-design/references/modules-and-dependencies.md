# Rust 模块与依赖

## 1. 软件包边界

软件包按可复用性、所有权和运行时依赖划分。可复用内核、组件、内存、虚拟化和驱动核心优先 `#![no_std]`；只有边界确实需要时才引入 `alloc`、`std` 或受功能开关控制的支持。

### 1.1 项目分层

可复用逻辑放在 `components/`、`drivers/`、`memory/` 或 `virtualization/`，操作系统适配放在使用它的 ArceOS、StarryOS、Axvisor 或平台层附近。驱动核心不直接依赖任务、文件系统或网络运行时；能力通过 `mmio-api`、`dma-api`、`rdif-*` 或明确适配层注入。

新软件包应有真实调用方和独立不变量。只为规避循环依赖、隐藏一个转发函数或预留未来扩展而新增软件包通常说明边界尚未找准。

### 1.2 模块与可见性

实现模块默认私有，只暴露有意设计的稳定入口。从 `lib.rs` 重新导出能够形成清楚公共表面时再重新导出，避免深层路径和根目录重复暴露同一对象。

大型源文件按领域和变化原因拆分。优先使用与模块同名的源文件加子目录；仅在现有布局和工具链要求时使用 `foo/mod.rs`。测试模块应遵循生产代码的可见性，不通过扩大公共接口来方便测试。

## 2. 条件编译与功能开关

条件编译位于真实边界上，例如平台实现、可选后端或宿主工具。公共入口在支持的组合中保持一致，不让调用方到处重复 `cfg`。未启用能力时返回明确不支持，或在编译期移除整个能力；不要保留会静默成功的空实现。

功能开关应单调且可组合。默认功能、`std` 支持和平台功能不能暗中改变同一接口的所有权或错误语义。新增组合要由项目静态检查矩阵覆盖。

## 3. 依赖管理

存在 `[workspace.dependencies]` 和工作区软件包名时使用它们。优先采用工作区统一版本与功能；`no_std` 依赖除非确有需要，关闭默认功能并显式选择能力。

### 3.1 来源与发布

避免临时 Git、绝对路径、仓库外路径或非预期注册表覆盖。需要发布的软件包，其普通依赖必须具有可由 crates.io 解析的版本；工作区路径可以与版本并列，但不能只依赖不可发布路径。

依赖升级或来源切换要检查公共类型是否来自同一软件包实例、功能是否改变、重复版本是否造成类型割裂，以及许可证和目标平台支持。不要通过根补丁掩盖边界错误类型不一致，优先显式转换。

### 3.2 依赖方向

低层领域软件包不能依赖高层操作系统或工具编排。共享抽象应由能力拥有者定义，而不是为了消除循环依赖创建无领域语义的公共杂物软件包。

## 4. 宏与诊断

宏适合消除具有统一语法和不变量的重复，不适合隐藏控制流、资源所有权或错误传播。能用函数、泛型、常量或派生完成时优先使用语言机制。

### 4.1 宏接口

导出的宏使用 `$crate` 定位自身项目，避免依赖调用方导入；为表达式和模式选择准确片段类型；临时标识符避免与调用方冲突。宏展开后的错误信息应能指向调用点或清楚说明契约，不生成难以理解的嵌套类型错误。

宏修改要测试多个调用位置、可见性、重命名依赖、条件编译和错误输入。只测试展开后的一个成功示例不能证明公共宏稳定。

### 4.2 可诊断性

公共类型在不泄漏敏感或无界内容的前提下提供有用的 `Debug`。状态机、协议和硬件错误应保留阶段、对象和原始状态，方便从持续集成或板卡日志追踪；不要让诊断格式成为另一个需要解析的隐式接口，除非它本来就是明确的机器输出契约。
