# AxVisor 网页配置编辑

## 1. 配置与客户机

网页管理的 TOML 是下一次创建客户机的输入，不是已注册实例的可变状态。`GuestConfig` 继续拥有持久化字段与配置内校验；`vm_pool` 拥有文件扫描和保存，管理器继续独立拥有实例生命周期。编辑保存不调用管理器的创建、停止或重新配置操作。

### 1.1 工作入口

`VmsPanel` 保留按构建默认值快速创建客户机的入口，自动 ID 的语义仍由现有 `fields` 请求负责。配置库中的新建、编辑、查看与另存为使用同一个配置编辑器，完整配置通过现有 `toml` 请求创建实例或保存为候选文件；完整 TOML 中的 ID 仍是显式值。

内置配置和不属于可写池目录的配置只允许查看和另存为。动态条目的可编辑性由后端返回的 `editable` 字段说明，前端不得仅凭文件扩展名判定可写。已注册实例对应的源文件可以编辑，但界面须说明保存不改变该实例，下一次重新创建才使用新配置。

### 1.2 Schema 来源

`axvmconfig::GuestConfig` 的 Schemars 派生是完整配置 JSON Schema 的来源。宿主工具 `cargo xtask axvisor config vm-schema --output <文件>` 生成 Draft 7 Schema；开发快照位于 `os/axvisor/web-ui/src/generated/guest-config.schema.json`，`web_ui::build_dist` 在暂存前端中重新生成同一路径后打包。不得在 AxVisor 内核启用宿主 `std` 或手写第二份持久化字段定义。

现有 `GET /api/vms/schema` 的 `fields` 保持兼容。快速创建把这些字段适配为标准 JSON Schema，复用完整配置编辑器的表单渲染基础，而不是维护第二套控件。字段标签、分组和帮助属于界面元数据，不改变配置的类型与约束。

`VirtualDeviceRequest` 的模型私有选项不由通用 Schema 穷举。编辑器必须保留开放参数，提供显式的结构化或 TOML 编辑入口，不将未描述字段清除，也不声称已完成模型专有校验。后端解析与启动准备仍负责最终业务校验。

Schema 描述配置的规范序列化形式，不一定覆盖 Serde 接受的所有兼容输入。例如现有内存区域可使用四元素数组，而规范形式是具名对象。`config_normalize` 能力声明 `POST /api/vms/config/normalize`，接收 `{ "toml": "..." }`，通过 `GuestConfig::from_toml` 和现有序列化器返回 `{ "toml": "..." }`；非法输入返回带 `error` 的 400，内部序列化失败返回 500。它不写文件、不访问管理器、不检查镜像是否已就位，也不改写持久化格式规则。

以数字序列化的 `VmMemMappingTypeSerde` 使用 `JsonSchema_repr` 派生，使 Schema 的枚举与既有 `serde_repr` 编码一致；此修正不改变 TOML 接受值或运行期映射类型。

## 2. 草稿与视图

配置编辑器以未提交草稿为唯一编辑状态。可视化与 TOML 是该草稿的两种视图，不是两份独立配置；`ConfigEditor` 负责模式切换与转换，外层对话框负责文件名、保存方式和请求状态，基础 Schema 表单只负责输入与字段错误。

### 2.1 转换规则

打开配置和只切换视图时保留 TOML 原文，包括注释与数字写法。可视化修改后允许规范化 TOML，但必须在修改前说明注释和格式的影响。解析或转换失败不替换草稿；无法安全表示的整数、日期等值必须保真处理，或明确阻止进入可视化修改而保留源码模式。

已有或粘贴的非空配置进入可视化前，先通过 `config_normalize` 获取规范形式，用它生成表单数据，但草稿源码仍保留操作者原文。网络失败或后端拒绝时保留源码并显示原因；请求结果只能应用到发起时的同一草稿，关闭、后续输入和新请求须使旧结果失效。空白新建从 Schema 开始填写，不要求尚未填完的草稿先通过后端。缺少该能力的后端对旧配置仅提供源码编辑，不猜测兼容字段转换。

表单不得开启删除额外数据的选项。未知字段、设备扩展字段与嵌套数组经过编辑后必须保留；不能安全表达的开放字段可使用明确标注的 TOML 子编辑器。校验失败时保留输入并显示原因，不通过补默认值或删除字段使错误消失。

### 2.2 提交与退出

对话框区分加载、可编辑、提交中、提交失败和成功状态。加载支持重试；提交期间禁止重复请求与退出；失败保留草稿。只有成功才关闭并刷新配置库。脏草稿通过取消、关闭、Esc 或点击遮罩离开时需要确认，恢复未修改状态后不再提示。

桌面使用宽屏分组工作区，窄屏允许纵向滚动；操作区保持可见。帮助信息默认收起，错误与会影响用户决定的只读、覆盖和运行实例提示保持可见。控件须有标签、键盘焦点和可关联的错误信息。

## 3. 文件更新

新增更新能力只扩展文件保存，不改变原有新增接口。`POST /api/vms/pool` 仍以 `create_new` 保存，重名返回冲突；更新通过能力表 `pool_update` 声明的 `POST /api/vms/pool/update` 提交，前端通过访问器取 URL。

### 3.1 请求与结果

更新请求为 `{ "path": "...", "expected_toml": "...", "toml": "..." }`。`path` 是已读取配置的绝对路径，`expected_toml` 是打开时读取的完整原文，`toml` 是待保存草稿；成功返回 `{ "path": "..." }`。后端先验证路径及新配置，再在现有 `SAVE_LOCK` 内比较当前文件和原文，拒绝基于旧快照的覆盖。

更新只允许池写入目录及其非隐藏子目录内的普通 `.toml` 文件，排除内置树、传输暂存目录、路径穿越、非规范路径、符号链接和非普通文件。`editable` 使用相同的后端判定，包括底层文件系统的替换支持。池外来源即使可扫描也不因此获得写权限。

拒绝语义必须对用户可见：非法路径或配置为 400，禁止修改的来源为 403，原文件不存在为 404，原文不匹配为 409，文件系统失败为 500。错误响应携带可读 `error`，不得把缺失、只读和并发冲突全部折叠成“保存失败”。

### 3.2 替换与失败

`vm_pool` 使用同目录独占暂存文件写入新内容，完成后通过文件系统支持的替换重命名提交。提交前写入失败只清理本次暂存文件，不删除、截断原文件，也不退回原地覆盖；不支持替换时返回明确失败。对 API 更新的互斥由 `SAVE_LOCK` 提供，不能宣称它能阻止任意宿主 shell 绕过 API 同时写入。

当前支持范围限于已核实替换实现的内建 ext4、tmpfs 和 ramfs；其他文件系统在创建暂存文件之前拒绝更新，`editable` 也使用同一限制。FAT 的普通重命名可能先移除目标，不能用于此流程；新增后端需要先核对其真实替换语义，不能只依靠通用 API 名称推定安全。

此操作不提供掉电事务或跨多个文件原子更新保证，不增加文件格式迁移。用户可保留旧 TOML，使用同一更新流程回退配置；若原文已变化，仍需重新读取并显式处理冲突。

ext4 的命名空间替换可能已经完成，随后才报告回收或同步错误。因此重命名报错时返回明确的“提交结果可能已生效，请重新读取”提示，不删除残留暂存文件，不擅自回滚或自动重试；用户先重新读取最终路径，再决定下一步。不能把所有 I/O 错误都解释成“没有提交”，也不能承诺存储故障下的旧内容永久保留。

## 4. 验证边界

前端转换测试证明草稿保留、嵌套结构与开放参数不丢失、非法输入拒绝及数值安全。真实浏览器验证页面布局、键盘和保存后的重读；不能用仅运行转换函数替代用户流程。

### 4.1 文件与接口

复用配置池保存集成测试证明新建与更新的完整操作：成功后重新读取，旧原文冲突及非法配置不改原文件，内置/池外路径不能更新。HTTP/QEMU 证明能力声明、状态码与打包资源可以被真实前端使用，不重复穷举底层字段校验。

### 4.2 交付证据

使用项目 `cargo xtask` 和前端现有 npm 入口验证受影响范围。主代理在真实 AxVisor QEMU 后端上操作默认创建、完整新建、编辑重读、另存为、错误和取消流程，截图保存在会话产物目录，经 GitHub 上传后引用于 PR，不将截图或浏览器临时脚本加入源码。
