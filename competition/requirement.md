赛题名称：智能化工控中基于虚拟化的混合系统部署及联动实现
背景描述
工业控制系统正在向智能化、网络化发展，需要在有限硬件资源上同时兼顾实时控制、智能计算和安全隔离。本赛题希望参赛队伍基于虚拟化技术，探索 AI 应用与 RTOS 控制任务协同运行的实现方式。

目标
基于 tgoskits 项目（https://github.com/rcore-os/tgoskits）中的 AxVisor，构建一个智能控制演示平台：在同一硬件或仿真平台上运行 Linux/Starry 客户机和 RTOS 客户机，实现跨客户机通信，并演示 AI 模型对控制参数或控制策略的动态调整。

起始基线说明
参赛队伍以 tgoskits 项目的 dev 分支为起点。项目已具备以下基础能力：

AxVisor 可在 QEMU（aarch64/riscv64）上启动多客户机
已支持 RT-Thread 作为 Guest OS
已支持飞腾派、ROC-RK3568-PC、香橙派 5 Plus、RDK S100P 等开发板
已有 VirtIO、vsock、HyperCall 等基础机制
StarryOS 已支持运行 Linux 用户态程序
参赛作品应在上述能力基础上完成定制与扩展。

# 任务要求
## 任务一：实时性改造与验证
面向实时系统需求改造 AxVisor，优化调度、抢占、定时器、中断路径、CPU 亲和性、锁临界区或后台任务等关键路径，提升确定性和最坏情况响应能力。
基于改造后的 AxVisor 启动不少于 2 个 vCPU 的多核 Linux 客户机，并说明 vCPU/物理 CPU 绑定、内存分配、设备映射、中断路由和启动参数。
建立实时性验证流程，测量周期任务抖动、调度延迟、中断响应延迟、最大延迟和长时间稳定性，并提供测试命令、运行时长、CPU 负载分布和结果数据。
选择 Zephyr、RT-Thread、FreeRTOS 等至少一种裸机或原生 RTOS 作为基线，在相同或等价平台运行同类周期任务和压力测试，并说明平台差异对结果的影响。
提供分支、镜像、配置、构建与启动命令、测试脚本、RTOS 基线配置和结果采集方式，确保可复现。
## 任务二：客户机间通信
在 Starry/Linux 客户机和 RTOS 客户机之间建立基于 IP 协议栈的双向网络链路，可采用虚拟网卡、桥接、用户态网络或实际网口；共享内存、HyperCall、裸 MMIO 等非网络机制不得作为主数据通道。
设计运行在 TCP/UDP/IP 或等价 IP 传输之上的应用层协议，并实现 Linux/RTOS 两端程序。协议应包含版本、消息类型、载荷长度、序号或时间戳、错误码或校验字段，并支持控制指令、状态回传和错误通知。
vsock 默认不计入主要网络通信通道；如使用 vsock，仅可作为辅助控制、调试或扩展对比，并需在设计文档中明确边界。
针对所选传输实现可靠性机制：UDP 等不可靠传输需支持 ACK、超时、重传、乱序或重复包处理；TCP 等字节流传输需支持消息分帧、连接超时、断连重连和异常恢复。
在设计和测试文档中说明网络拓扑、MAC/IP 地址、路由、端口、桥接或 NAT 规则、防火墙或访问控制策略，并统计请求成功率、应用层错误、超时、异常恢复、请求-响应延迟和有效应用吞吐量等指标。
## 任务三：AI 模型与控制联动
在 Starry/Linux 客户机中部署包含神经网络推理环节的 AI 应用，并通过任务二定义的网络协议向 RTOS 客户机发送模型输出。
RTOS 客户机根据 AI 输出调整控制参数或控制策略，并执行可观察的控制动作，例如日志、虚拟外设、LED、PWM 或电机控制。
演示链路需形成完整闭环：AI 输入、模型推理、跨客户机网络通信、RTOS 控制输出、状态回传或效果展示。
测量并报告端到端延迟，说明测量方法、误差来源和精度范围；可采用同侧往返测量、共享时间源，或 Linux/RTOS 时钟同步后基于协议时间戳统计跨客户机耗时。
设计可量化演示场景，以固定参数手动控制作为基线，对比 AI 参与后的控制效果差异，至少包含两项指标，例如响应延迟、控制误差、稳定时间或识别准确率。

# 最终提交材料
设计文档：系统架构、客户机配置与修改说明、通信协议规范、隔离设计、AI 模型选型及部署方式。
测试文档：启动验证、通信可靠性测试数据、性能基准数据、隔离性说明、端到端延迟测量方法与数据、控制效果对比。
源码：所有源码均以 PR 形式提交 tgoskits 仓库的 dev 分支，且没有冲突（暂时不要做）
复现说明：构建步骤、依赖环境、QEMU 启动命令、镜像生成方式。
演示视频：5 分钟左右，展示双终端交互、通信数据流动、AI 与控制联动效果。
