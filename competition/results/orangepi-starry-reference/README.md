# Orange Pi 5 Plus StarryOS/Zephyr reference

This directory retains one complete 1,800-command run and one 20-command
smoke run of the physical competition topology:

```text
Orange Pi 5 Plus / RK3588 / AxVisor

pCPU1 <- StarryOS vCPU0       pCPU2 <- StarryOS vCPU1
pCPU0 <- Zephyr vCPU0         pCPU3 <- AxVisor housekeeping

StarryOS 10.0.0.1/24 -- virtio-net -- isolated segment 1 -- virtio-net -- 10.0.0.2/24 Zephyr
```

StarryOS runs the checked-in neural controller as a Linux-ABI userspace
program. Zephyr applies each UDP/IPv4 `IVC/1` command exactly once, advances
the thermal plant, and returns STATUS plus ACK. No host-facing NIC, bridge,
NAT, vsock, shared-memory channel, or hypercall channel carries application
data.

## Results

Both commands exited successfully only after the analyzer validated the
application records and the board runner restored Linux.

| Full-loop p50 / p95 / p99 / max | 4,694 / 6,952 / 6,952 / 8,915 us | 6,751 / 11,265 / 11,695 / 14,405 us |

| Host filesystem synchronized | yes | yes |
| TF-card Linux restored | yes | yes |

The full run reproduces the neural control result from the QEMU reference:
RMSE `5,932.491 mC`, integrated absolute error `686,993.400 mC*s`, and maximum
overshoot `13,428 mC`. The smoke trajectory is intentionally too short for a
meaningful control-quality comparison.

StarryOS reported two online vCPUs and configured `eth0` as `10.0.0.1/24`.
Its sysfs MAC lookup returned `unknown` in the autorun shell, while the StarryOS
network initialization record and the virtio configuration both pin the
interface to `52:54:00:00:00:01`. Zephyr validates
`52:54:00:00:00:02` at startup.

## Evidence and integrity

- `full-summary.json` and `smoke-summary.json` were generated by
  `competition/ivc/analyze_board.py`.
- `*-console.log.gz` is deterministic gzip (`gzip -n -9`) of the complete
  board build, U-Boot, AxVisor, guest, shutdown, power-cycle, and Linux-restore
  console capture.
- `metadata.json` records source state, environment, artifact/configuration
  hashes, UTC intervals, raw-log hashes, and compressed hashes.

Expected uncompressed log hashes are:

```text
full   023ff07b40b4936453eee6d4bbd57bca1c1699e7305dc1af5fe601a5d67492d9
smoke  8dd16dbcc7608305da9fcf13f393a54e410e16ef26da63ca5c2821878efbf265
```

Verify and re-analyze without normalizing ANSI bytes or line endings:

```sh
gzip -cd full-console.log.gz > /tmp/ivc-orangepi-starry-full.log
sha256sum /tmp/ivc-orangepi-starry-full.log
python3 ../../ivc/analyze_board.py \
  /tmp/ivc-orangepi-starry-full.log \
  --expected-count 1800 \
  --output /tmp/ivc-orangepi-starry-full-summary.json
```

The shared physical UART can lose spans when multiple guest/host consoles are
active. Controller and RTOS terminal metrics are therefore split into short
records, emitted twice with pacing, and accepted only when at least one
complete copy exists and all complete copies agree. The analyzer separately
requires StarryOS completion, RTOS poweroff, AxVisor filesystem-sync
confirmation, and board Linux restoration. It does not infer missing metrics
from a success marker.

## Reproduction entry points

From the WSL2 repository root, build and stage the finite guest artifacts:

```sh
bash competition/ivc/starry/build.sh

ORANGEPI_SSH_TARGET=orangepi@<board-ip> \
ORANGEPI_SSH_IDENTITY=<ssh-private-key> \
  bash competition/ivc/stage-orangepi-5-plus.sh
```

Then run the maintained automation entry point with the root selector observed
from the board's Linux system:

```sh
export ORANGEPI_AXVISOR_HOST_ROOT=PARTUUID=<board-linux-root-partuuid>

bash competition/ivc/run-orangepi-5-plus.sh smoke
bash competition/ivc/run-orangepi-5-plus.sh full
```

By default, each command retains its latest log and JSON under
`tmp/competition/ivc/orangepi-last`. Set `ORANGEPI_IVC_RESULT_DIR` to retain a
different run directory. These two hardware observations demonstrate the
complete physical data/control and recovery path; they are not a repeated
statistical campaign or a general hard-real-time guarantee.
