● 问题出在哪里(一句话版)

  emulated(gppt)模式下,guest 的 GICR 写操作会被原样转发到物理 
  redistributor。Zephyr 启动时按标准流程写 GICR_ICENABLER0=0xffffffff,把 pCPU3
  上 host 自己的
  IPI(SGI0)给禁用了——virtualization/arm_vgic/src/v3/vgicr.rs:227-230 只保护了
  maintenance 中断(bit25),保护 SGI 的那行代码被注释掉了(// value &= !(1 << 
  SGI_IPI_ID);,连常量都不存在了)。所以 guest 一启动完,host 的 kick
  通道就物理级关闭:IPI 全部石沉大海 → 无 guest exit → 无 drain/inject → 64
  槽队列填满 → 236 次 overflow → guest received=0。日志规律完全吻合:guest 没跑到
  GIC init 的轮次 IPI 300/300 全通,跑到了的轮次 host_irq_received
  归零。这个机制两位专家到最后都没找到。

  Codex(gpt-5.6-sol)的判断

  正确的:

  1. passthrough 模式的根因:passthrough 下不开 HCR_EL2.IMO,SGI0 直接路由到 guest
  EL1、不会 trap 到 EL2——这条完全正确,解释了 A1 和 B-passthrough
  全灭,也是全场质量最高的发现。
  2. GICR pcpu_id 错配:配置写的 pcpu_id=0 但 vCPU 绑在 pCPU3,VGICR 转发到了错误
  CPU 的 redistributor,导致 guest 找不到匹配的 GICR
  起不来。定位准确、修复(改成 3)后 guest 成功启动,有运行证据闭环。
  3. 驳回 DeepSeek 的 DAIF 假设:指出 guest 运行期的 PSTATE 来自
  SPSR_EL2+ERET,不是简单继承 host 入口的 DAIF,拒绝在没证据前移动
  daifclr。事后证明完全正确——阻塞在物理 GIC 层,和 DAIF 无关,而且那是个影响所有
  AArch64 guest 的高风险改动。
  4. 戳穿 DeepSeek 误读日志:用统计脚本复核 /tmp/ab-emu-delay.log 实际
  guest_received=0,不是
  COMPLETE。对外部专家结论"逐条与本地证据核对"的做法本身也是对的。
  5. 把断点收敛到 "IPI → guest exit"(最后阶段):失败轮

  6. 回滚两次无效的 vGIC 尝试(allow-SPI 48、GICD_CTLR
