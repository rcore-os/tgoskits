## 赛题概述

**赛题名称：智能化工控中基于虚拟化的混合系统部署及联动实现**

工业控制系统正在向智能化、网络化发展，需要在有限硬件资源上同时兼顾实时控制、智能计算和安全隔离。本赛题要求参赛队伍基于 `tgoskits` 项目中的 **AxVisor**，在同一硬件或仿真平台上运行 Linux/Starry 客户机和 RTOS 客户机，实现跨客户机通信，并演示 AI 模型对控制参数或控制策略的动态调整。

三个任务构成一条完整技术链路：

1. 改造 AxVisor，建立可验证的实时运行基础。
2. 建立 Starry/Linux 与 RTOS 客户机之间的双向 IP 网络通信。
3. 在通信链路上完成“AI 推理—控制指令—RTOS 执行—状态回传”的闭环。

---

## 起始基线

参赛队伍以 [`tgoskits`](https://github.com/rcore-os/tgoskits) 项目的 `dev` 分支为起点。赛题给出的已有能力包括：

- AxVisor 可在 QEMU `aarch64`、`riscv64` 平台上启动多客户机。
- 已支持 RT-Thread 作为 Guest OS。
- 已支持飞腾派、ROC-RK3568-PC、香橙派 5 Plus、RDK S100P 等开发板。
- 已有 VirtIO、vsock、HyperCall 等基础机制。
- StarryOS 已支持运行 Linux 用户态程序。

> ⚠️ 参赛作品应在这些已有能力上完成定制与扩展，而不是仅重复现有启动或演示流程。

## 任务一：实时性改造与验证

### 任务目标

面向实时系统需求改造 AxVisor，提升系统运行的**确定性**和**最坏情况响应能力**，并以可复现的实验数据验证改造成效。

### 具体要求

1. 分析并优化调度、抢占、定时器、中断路径、CPU 亲和性、锁临界区或后台任务等关键路径。
2. 基于改造后的 AxVisor 启动不少于 **2 个 vCPU** 的多核 Linux 客户机，并说明：
   - vCPU 与物理 CPU 的绑定；
   - 内存分配；
   - 设备映射；
   - 中断路由；
   - 启动参数。
3. 建立实时性验证流程，测量并报告：
   - 周期任务抖动；
   - 调度延迟；
   - 中断响应延迟；
   - 最大延迟；
   - 长时间稳定性。
4. 测试材料需要记录测试命令、运行时长、CPU 负载分布和结果数据。
5. 选择 Zephyr、RT-Thread、FreeRTOS 等至少一种裸机或原生 RTOS 作为基线，在相同或等价平台上运行同类周期任务与压力测试，并解释平台差异对结果的影响。
6. 提供代码分支、镜像、配置、构建与启动命令、测试脚本、RTOS 基线配置和结果采集方式，确保实验可复现。

### 对应评分点（30 分）

| 评分点 | 分值 |
|---|---:|
| 实时化目标和关键路径分析清楚 | 4 |
| 对调度、抢占、定时器、中断或锁等关键机制有实质改造 | 8 |
| 多核 Linux 客户机稳定启动，CPU、中断和内存配置合理 | 4 |
| 改造前后数据完整，体现最坏情况延迟或抖动改善 | 5 |
| 空载与 stress 压力场景对比充分 | 4 |
| 与原生 RTOS 基线的对比合理且可复现 | 5 |

### 后续需要深入的问题

- [ ] 选择哪些关键路径作为首轮改造对象？
- [ ] 使用什么工作负载和测量工具建立可信基线？
- [ ] 如何保证 AxVisor 改造前后、原生 RTOS 之间的实验条件可比？
- [ ] QEMU 验证与真实开发板验证分别承担什么角色？

## 任务二：客户机间通信

### 任务目标

在 Starry/Linux 客户机和 RTOS 客户机之间建立基于 **IP 协议栈**的双向网络链路，并实现具备明确协议边界、可靠性机制和量化测试结果的应用层通信。

### 具体要求

1. 通信链路可以采用虚拟网卡、桥接、用户态网络或实际网口。
2. 共享内存、HyperCall、裸 MMIO 等非网络机制不得作为主数据通道。
3. 在 TCP/UDP/IP 或等价 IP 传输之上设计应用层协议，并实现 Linux/RTOS 两端程序。协议至少包含：
   - 版本；
   - 消息类型；
   - 载荷长度；
   - 序号或时间戳；
   - 错误码或校验字段。
4. 业务协议需要支持控制指令、状态回传和错误通知。
5. vsock 默认不计入主要网络通信通道；如果使用，只能作为辅助控制、调试或扩展对比，并在设计文档中明确边界。
6. 针对传输方式实现可靠性机制：
   - UDP：ACK、超时、重传、乱序包或重复包处理；
   - TCP：消息分帧、连接超时、断连重连和异常恢复。
7. 在设计与测试文档中说明：
   - 网络拓扑；
   - MAC/IP 地址；
   - 路由与端口；
   - 桥接或 NAT 规则；
   - 防火墙或访问控制策略。
8. 统计请求成功率、应用层错误、超时、异常恢复、请求—响应延迟和有效应用吞吐量等指标。

### 对应评分点（25 分）

| 评分点 | 分值 |
|---|---:|
| Starry/Linux 与 RTOS 间 IP 网络链路建立且配置清楚 | 4 |
| 应用层协议字段完整，并运行在明确的网络传输之上 | 5 |
| 控制指令、状态回传、错误通知三类消息可用 | 5 |
| 可靠性、超时、重连或异常恢复机制有效 | 4 |
| 自动化测试数据充分 | 4 |
| 网络隔离与访问控制说明或验证合理 | 3 |

### 后续需要深入的问题

- [ ] 主传输选择 TCP 还是 UDP，选择依据是什么？
- [ ] 网络设备由 AxVisor 原生提供、透传，还是通过其他后端实现？
- [ ] 协议如何定义状态机、兼容性、错误语义和重试幂等性？
- [ ] 如何注入丢包、乱序、断连和客户机重启，形成确定性测试？

## 任务三：AI 模型与控制联动

### 任务目标

在 Starry/Linux 客户机内运行包含神经网络推理环节的 AI 应用，通过任务二定义的网络协议驱动 RTOS 控制任务，并形成可观察、可测量、可与固定参数方案对比的完整闭环。

### 具体要求

1. 在 Starry/Linux 客户机中部署包含神经网络推理环节的 AI 应用。
2. 通过任务二定义的网络协议向 RTOS 客户机发送模型输出。
3. RTOS 根据 AI 输出调整控制参数或控制策略，并执行可观察动作，例如：
   - 日志输出；
   - 虚拟外设；
   - LED；
   - PWM；
   - 电机控制。
4. 演示完整闭环：**AI 输入 → 模型推理 → 跨客户机网络通信 → RTOS 控制输出 → 状态回传或效果展示**。
5. 测量并报告端到端延迟，说明测量方法、误差来源和精度范围。可选方案包括：
   - 同侧往返测量；
   - 使用共享时间源；
   - Linux/RTOS 时钟同步后，基于协议时间戳统计跨客户机耗时。
6. 设计可量化的演示场景，以固定参数手动控制为基线，对比 AI 参与前后的控制效果。
7. 对比至少包含两项指标，例如响应延迟、控制误差、稳定时间或识别准确率。

### 对应评分点（25 分）

| 评分点 | 分值 |
|---|---:|
| Starry/Linux 客户机中完成神经网络模型推理 | 4 |
| 模型输出通过任务二的网络协议发送给 RTOS | 5 |
| RTOS 根据 AI 输出执行可观察的控制动作 | 5 |
| 状态回传或效果展示形成完整闭环 | 4 |
| 端到端延迟测量方法合理且数据完整 | 3 |
| 与固定参数手动控制基线完成至少两项指标对比 | 4 |

### 后续需要深入的问题

- [ ] 选择什么控制场景，才能同时体现 AI 的必要性和 RTOS 的实时性？
- [ ] 模型输入、输出和 RTOS 控制量如何定义？
- [ ] AI 模型、推理框架、算力需求和客户机资源预算如何匹配？
- [ ] 如何拆分推理耗时、通信耗时、RTOS 响应耗时与执行耗时？

## 统一提交材料

- **设计文档**：系统架构、客户机配置与修改说明、通信协议规范、隔离设计、AI 模型选型及部署方式。
- **测试文档**：启动验证、通信可靠性测试数据、性能基准数据、隔离性说明、端到端延迟测量方法与数据、控制效果对比。
- **源码**：所有源码均以 PR 形式提交到 `tgoskits` 仓库的 `dev` 分支，且没有冲突。
- **复现说明**：构建步骤、依赖环境、QEMU 启动命令、镜像生成方式。
- **演示视频**：约 5 分钟，展示双终端交互、通信数据流动、AI 与控制联动效果。

### 跨任务评分项（20 分）

| 评分项 | 分值 | 核心要求 |
|---|---:|---|
| 工程完整性与文档 | 15 | 设计方案、测试文档、源码与配置完整，复现说明可操作 |
| 系统创新与扩展性 | 5 | 方案有创新，可扩展到更多客户机、RTOS 或控制场景，工程质量良好 |

### 加分项（最多 10 分）

| 加分项 | 分值 | 要求 |
|---|---:|---|
| StarryOS 代替 Linux | 4 | 选择 StarryOS 代替 Linux 完成上述任务 |
| StarryOS 完善 | 4 | 添加 syscall 完善 StarryOS，并合并到 `tgoskits` 的 `dev` 分支；按数量计分 |
| 更完整基线 | 2 | 同时完成多种 RTOS 或多种开发板对比 |

### 其他约束

- `tgoskits` 采用 Apache-2.0 许可证，参赛修改部分须以 Apache-2.0 开源。
- 允许使用 YOLO、ONNX Runtime、ncnn 等开源框架以及厂商 NPU SDK。
