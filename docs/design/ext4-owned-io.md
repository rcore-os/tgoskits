# ext4 锁外 I/O 与挂载级回写设计

## 问题、范围与验收

并行编译会同时读取源文件、查询目录、创建目标文件和写入构建结果。原适配层让这些操作与日志提交共用整个挂载的状态锁，磁盘等待会阻塞其他 inode 上的工作；普通目录修改还会触发同步提交。

本改动将可以独立执行的设备操作交给拥有完整资源的请求对象，并保留串行的元数据发布边界。目标是：一个文件的数据 I/O 或一次日志提交等待设备时，其他文件和目录仍可推进；显式同步、同步写和卸载仍满足持久化要求，失败不得丢失脏数据或误报成功。

不包含页表、调度器、设备驱动、磁盘格式、日志格式和格式化器批处理优化。不承诺所有 ext4 操作都已脱离挂载锁：旧式 indirect 写入、部分目录枚举和部分元数据操作继续使用串行路径。性能收益必须通过相同条件下的实际工作负载比较，不能从锁拆分直接推导百分比。

此设计改变并发所有权、默认回写时机和持久化边界，属于高风险改动。合入前需要文件系统和并发领域维护者先审核本文，再审核实现和验证证据。

## 既有实现与替代方案

基于 `1f408d1cff3cc251157829f5cfd19e91a53ad56c` 的 `dev`：复用原有块缓存一致性、设备生命周期、文件页缓存、映射撤销、目录缓存和只读挂载检查，不移植另一套全局缓存或设备运行时。

开放的 [#2015](https://github.com/rcore-os/tgoskits/pull/2015) 在检查时的 head 为 `6d5cc09f45a073680a270ae0b6047b24fd9eaff5`，主要处理 mkfs 批量清零、数据块缓存批量淘汰、同块 inode 预填充和小块延迟写入。本设计处理请求所有权与提交期间并发，不复制这些改动。两者会修改相同核心文件；后续整合必须按语义重放，不能直接覆盖缓存和 journal 实现。

| 方案 | 结果与取舍 |
| --- | --- |
| 保留全挂载串行同步 | 所有权简单，但不解决磁盘等待阻塞其他 inode 的问题。 |
| 只更换锁或减少调用 `sync` | 无法证明锁释放后的映射、inode 和事务仍有效，也缺少定期回写及卸载闭环。 |
| 为每个请求复制整个文件系统 | 产生多个元数据事实来源，事务与缓存合并复杂且容易覆盖新状态。 |
| 拥有型请求、短期状态锁、单一提交者 | 选用。元数据仍由一个挂载所有者管理，请求只携带本次 I/O 所需资源；代价是准备/执行/完成协议、代际校验和明确的关闭流程。 |

## Linux 对照

参考 Linux commit `980ab36ae5972c83f683b939e50c469c4947229e`，借鉴状态和持久化顺序，不复制 Linux 运行时或锁类型。

- [JBD2 提交状态切换](https://github.com/torvalds/linux/blob/980ab36ae5972c83f683b939e50c469c4947229e/fs/jbd2/commit.c#L546-L588)：把 RUNNING 事务转为 COMMITTING 后释放 `j_state_lock`，再发起数据与日志 I/O。新事务与正在提交的事务不共用可变状态。
- [JBD2 屏障和提交记录](https://github.com/torvalds/linux/blob/980ab36ae5972c83f683b939e50c469c4947229e/fs/jbd2/commit.c#L782-L824)：状态锁不跨设备 flush 和完成等待。
- [ext4 文件同步](https://github.com/torvalds/linux/blob/980ab36ae5972c83f683b939e50c469c4947229e/fs/ext4/fsync.c#L110-L188)：先等待文件数据，再等待所需日志事务，并传播回写错误。
- [同步写完成](https://github.com/torvalds/linux/blob/980ab36ae5972c83f683b939e50c469c4947229e/include/linux/fs.h#L2652-L2673)：只有数据写入完成且所需同步成功后，才返回成功字节数。
- [挂载和 inode 同步策略](https://github.com/torvalds/linux/blob/980ab36ae5972c83f683b939e50c469c4947229e/include/linux/fs.h#L2120-L2146)：已经打开的文件仍需观察共享挂载策略，不能只在打开时复制一次。

当前 `rsext4` 的 `fdatasync` 仍提交完整相关日志，不实现 Linux 每 inode 的 `i_datasync_tid` 最小提交范围；同步挂载或同步 inode 也可能做更强的元数据同步。保留持久化保证，但不能宣称具有 Linux 相同的最小 I/O 成本。

## 所有权与调用链

```text
文件/目录操作
  -> 保留 inode 生命周期与挂载操作许可
  -> inode 内容锁或目录命名空间锁
  -> 挂载状态锁内准备请求
  -> 释放挂载状态锁，独立设备端点执行 I/O
  -> 挂载状态锁内校验并发布结果
  -> 释放请求、内容/目录保护和操作许可

显式同步 / 后台回写
  -> 页缓存写回（不持有提交锁）
  -> 独占提交锁
  -> 状态锁内封存事务及生成带挂载身份的票据
  -> 状态锁外写 ordered data、日志与屏障
  -> 状态锁内校验票据并发布完成状态
```

### 设备与缓存

`FsBlockDevice::fork_io` 明确要求同一一致性域、几何、边界和持久化能力。原生块设备复制已有运行时句柄；缓冲设备复用同一块缓存并增加消费者引用；分区端点保留原来的块范围。最后一个消费者才负责最终缓存写回，不让一个临时请求的释放提前关闭设备。

`rsext4` 使用下层共享块缓存，避免独立端点绕过另一份私有脏块缓存。inode 元数据仍来自同一规范缓存；只读能力只用 `try_lock` 复制完整 inode，遇到忙、事务私有状态或已失效状态时回到受保护的正常读取路径，不在自旋锁内发起设备 I/O。

### 读取、写入与目录

独立读取携带映射及可见性版本。读取执行完毕后，在状态锁内核验身份和版本；陈旧结果重试，不发布。目录查找在核验成功的同一临界区内取得目标 inode 生命周期，不能把未保留的裸 inode 编号交给锁外调用者。

文件读者共享内容访问许可，写者独占。写请求保留映射拥有者直到数据完成和元数据接受；未写入的 extent 只在实际数据完成后转换。请求准备失败不发布部分所有权，完成阶段失败通过守卫回收尚未接受的请求。已排队写者阻止新读者不断抢占。

普通目录修改取得父目录独占许可与拓扑共享许可；rename/rmdir 取得拓扑独占许可。不同普通目录之间可并行，拓扑操作仍有单一序列化边界，不引入推测性的祖先锁协议。

### 日志提交

封存前完成所有可能失败的容量和端点准备。提交对象拥有本次封存的不可变元数据，不持有挂载状态引用；完成票据包含挂载身份和递增代际，陈旧或其他挂载的完成结果不能作用于当前事务。

提交完成只发布对应批次的进度和 checkpoint 状态，不覆盖后来 RUNNING 事务的修改。checkpoint 需要关闭相应日志接纳并排空旧批次，不能把已复用的日志空间提前宣布为可用。序号溢出返回错误。

挂载每五秒进行一次页缓存和日志回写。显式同步和后台任务使用同一提交协议；跨多个事务的元数据同步先封存有限前缀，避免持续新写入使同步永不结束。最后一个批次等待设备时不再禁止普通元数据操作。

## 锁顺序、关闭与失败

- 页缓存修改先取得缓存写许可，再取得原有映射和缓存 I/O 锁。页写回可请求日志推进，所以页缓存排空必须在提交锁之外。
- 内容/目录保护先于挂载状态锁；提交锁先于挂载状态锁。挂载状态锁内不得等待提交锁、内容锁或通知完成。
- IRQ 锁只保护许可计数和等待者登记；分配、通知和线程 join 在 IRQ 锁外进行。先登记、再重查等待条件，消除检查与睡眠间的丢失唤醒。
- 卸载依次关闭外部缓存修改、停止并 join 回写任务、排空页缓存、关闭内部操作、处理待回收 inode、停止 MMP，再排空日志并发布 clean 状态。
- 打开的已删除文件继续保留规范缓存身份，直到最后一个 inode 拥有者回收；不能因 unlink 就丢掉脏页索引。
- 页写回失败时保留脏状态。周期回写仍尝试提交已完成的有效前缀，但优先返回原始页错误。
- 日志失败锁存首个原因并禁止后续缓存写；记录 abort 状态的二次失败单独保留，不能替换最初原因。失败后重新开放卸载许可不清除永久错误。
- clean 状态只在数据、日志、checkpoint 与 MMP 条件满足后发布。此前失败可以恢复工作线程和操作许可；已经开始最终 clean 发布的失败不得伪装为正常重新挂载。

## 兼容、启用与回滚

普通可写挂载在阻塞任务运行时和独立设备能力都可用时启用后台回写，日志明确报告启用状态。缺少独立端点或任务运行时时，明确记录原因并保留原同步完成路径；其他初始化错误直接失败。只读挂载不启动写回任务。

普通 `write` 不再暗含立即持久化；`O_SYNC`、`O_DSYNC`、`MS_SYNCHRONOUS`、`MS_DIRSYNC` 和 ext4 inode 同步标志在相应完成边界生效。普通 remount 修改共享同步策略，bind-remount 不修改整个文件系统；目录同步标志不会被普通同步位切换意外清除。`statfs` 和 proc 挂载输出反映策略。

磁盘格式不变，没有迁移工具或不可逆格式升级。回滚需先成功同步并卸载，再切回旧内核；异常中断后的卷仍按既有日志恢复机制处理。出现回写错误、持续关闭失败或数据不一致时停止使用新写入路径并保留原始错误，不能通过忽略错误继续运行。

## 验证要求

组件测试验证真实核心和适配层的提交票据、陈旧完成拒绝、锁外进展、脏状态保留、卸载顺序、已删除文件回写与同步策略。设备替身只负责控制完成和注入错误，不替代文件系统实现。

真实系统验证复用 Starry QEMU 中的文件创建、同步、挂载、目录和缓存相关用例，并补充缺少的同步挂载可观察行为。只使用 QEMU，配置为八个虚拟 CPU、8 GiB 内存；不运行实体板卡。所有运行均在重构后的三轮静态检查完成后进行。

提交记录必须分别列出格式化、功能组合静态检查、组件测试和 QEMU 实际执行结果；尚未运行或证据不足的行为不得写为通过。低层锁外进展测试不能替代系统调用兼容性和实际并行编译验证。
