# 设备直接访存的一致性与无缓存别名设计

本文面向刚接触设备驱动和内存管理的读者。这里的“设备直接访存”是指硬盘控制器、网卡等设备直接读写内存，代码中使用通用缩写 `DMA`。

更偏使用方法的介绍见 [`docs/docs/architecture/memory/dma.md`](../docs/architecture/memory/dma.md)。本文重点说明这次改造为什么要做、各层分别负责什么，以及内存从申请到释放经历了哪些状态。

## 1. 要解决的问题

旧实现只要收到“一致内存分配”请求，就会把内核直映区中对应页面的缓存属性原地改成“不可缓存”。这样有两个问题。

第一，内核直映区可能使用 2 MiB 或 1 GiB 的大页。一次 4 KiB 分配如果落在大页内部，原地修改可能连带改变邻近页面。之后别的分配再把同一大页改回去，就会出现同一段物理内存被一部分代码当成可缓存、另一部分代码当成不可缓存的情况。

第二，并非所有设备都需要无缓存映射。在 RISC-V 模拟机器上，PCI 存储控制器与处理器自动保持缓存一致，普通连续内存就能直接使用。旧接口没有携带设备的一致性属性，仍然强制申请无缓存别名；当平台没有可用的别名地址范围时，NVMe 初始化就以 `NoMemory` 失败。这正是 #1775 暴露的核心问题。

另一方面，SG2002 等设备确实不能自动保持一致。提交描述符前如果不清理处理器缓存，设备可能读到旧内容；设备完成后如果不让处理器缓存失效，处理器也可能读到旧结果。因此不能把所有设备简单改成“一致”，而要让每台设备携带自己的真实属性。

## 2. 为什么底层内存同步接口不能单独解决

`someboot` 和 `somehal` 已经能够执行某个平台所需的缓存清理、失效和屏障。但这类函数只知道“怎样处理一段地址”，不知道下面这些设备语义：

- 这台设备是否自动保持缓存一致；
- 设备能够访问多大的地址范围；
- 设备地址是否经过转换，属于哪个地址空间；
- 这次传输是处理器写、设备读，还是设备写、处理器读；
- 当前内存由处理器持有还是设备持有；
- 设备是否已经真正停止，内存能否释放或复用。

如果每个驱动直接调用底层同步函数，这些判断就会散落到各处，容易出现漏同步、方向相反、重复同步，或对一致设备执行不必要操作。

因此职责分为五层：

1. 设备探测从设备树、固件表、总线信息或明确的平台配置中取得设备属性。
2. `dma-api` 保存完整设备描述，检查地址限制，并用所有权变化决定同步时机。
3. 驱动只表达“交给设备”和“设备已经停止并交还处理器”。
4. `axklib` 把请求连接到内核页分配、地址映射和缓存能力。
5. `somehal` 与 `someboot` 执行当前处理器真正需要的缓存和屏障操作。

底层同步接口仍然必需，但它只是最后一段平台实现，不是完整的设备直接访存接口。

### 2.1 上游内核采用的分层

Linux 也先用 `dev_is_dma_coherent` 确定设备属性，再由 `dma_direct_alloc` 选择分配路径：一致设备通常使用分配器原有映射，非一致设备才进入架构专用分配、预留一致内存池或单独重映射。arm64 的重映射路径先分配物理页，再建立独立处理器映射；释放时先删除别名，最后释放原始页。

Linux 的中转缓冲区实现也把“复制”和“缓存维护”分开：两类设备只要使用中转内存都要复制，只有非一致设备执行架构缓存操作。页表属性只修改大页的一部分时，arm64 会先拆分相交的大页，避免影响邻近页面。

本设计沿用这些职责边界，但使用 TGOSKits 自己的类型所有权表达请求状态，不照搬 Linux 的函数形状。

## 3. 设备信息只有一个来源

一台设备的完整描述统一放在 `DmaDeviceInfo` 中：

- `DmaDomainId`：设备地址属于哪个地址空间；
- `DmaCoherency`：设备与处理器是否自动保持缓存一致；
- `DmaConstraints`：地址范围、对齐、边界和单段长度限制。

`DeviceDma::new(info, op)` 只接受这份完整描述和系统后端，不再接受容易错位的零散参数。对外也只通过 `info()` 取回整份设备信息，不再为地址范围、地址空间和一致性分别提供同义入口。

块设备队列的 `QueueLimits` 同样只保存一个 `DmaDeviceInfo`。文件系统从队列取得原值，不再重新拼装设备地址空间、一致性和地址限制。网络队列、NVMe 队列、AHCI 队列等需要收紧限制时，只能取原限制和队列限制中更严格的一方，不能在修改地址范围时顺便丢掉原有对齐、边界或单段长度。

### 3.1 地址空间不再使用历史占位值

`DmaDomainId` 只有两种明确表达：

- `Direct`：设备地址就是物理地址。当前实现使用这一项。
- `Translated(编号)`：为以后接入设备地址转换保留的类型边界。

当前代码还没有建立真正的转换空间，因此不能随手填一个编号并声称已经完成地址转换或设备隔离。将来接入输入输出地址转换单元后，编号必须来自已经建立并绑定到设备的转换空间。

历史全局编号、数字零自动回退和 `new_legacy` 一并删除，避免一个看似有效的占位值掩盖真实能力缺失。

### 3.2 一致性是设备属性，不是处理器常量

`DmaCoherency::Coherent` 表示设备和处理器自动看到对方写入的内容。`DmaCoherency::NonCoherent` 表示所有权切换时需要平台缓存处理。

这个属性不应仅由处理器种类决定。同一台机器上的不同设备也可能不同。设备树路径需要沿设备的访存父节点查找 `dma-coherent` 或 `dma-noncoherent`；固件表路径需要按父子关系继承 `_CCA`；PCI 设备继承其宿主桥得到的属性。

## 4. 只保留一套上层所有权接口

普通连续缓冲区和临时映射缓冲区只公开两种范围操作：

- `prepare_for_device(范围)`：处理器已经写完，把这段内存交给设备；
- `complete_for_cpu(范围)`：设备已经停止，把这段内存交还处理器。

不再同时提供 `sync_for_device`、`sync_for_cpu` 和只做转调的整块兼容入口。底层后端仍保留缓存同步能力，但驱动不直接用它表达请求生命周期。

异步块请求进一步用类型表示状态：

```text
CpuDmaBuffer
    -> PreparedDma
    -> InFlightDma
    -> CompletedDma
    -> CpuDmaBuffer
```

- `CpuDmaBuffer`：处理器持有，可以读写，但还没有交给设备。
- `PreparedDma`：缓存处理已完成，尚未提交硬件。
- `InFlightDma`：设备可能正在访问，不能安全释放。
- `CompletedDma`：已经确认设备停止，结果对处理器可见。
- `QuarantinedDma`：无法确认设备是否停止，只能隔离，不能重新交给分配器。

普通数据复制只复制，不再偷偷执行第二次同步。真正的缓存动作只发生在上述所有权变化处。

## 5. 一致设备的分配路径

一致设备收到“一致内存分配”请求时，直接使用普通物理连续分配：

1. 分配连续页面；
2. 使用原有内核映射作为处理器地址；
3. 使用这些页面的物理地址作为设备地址；
4. 发布包含处理器地址、分配器地址、设备地址和布局的句柄。

这条路径不建立无缓存别名，也不执行多余缓存维护。释放时把同一地址交回连续页分配器。它直接解决了 #1775 中 RISC-V 模拟机器的 NVMe `NoMemory` 问题。

“不需要缓存维护”并不等于“不需要顺序保证”。驱动在写设备寄存器前、读取完成结果后，仍要执行设备协议要求的内存屏障。

## 6. 非一致设备的无缓存别名路径

非一致设备需要一块处理器和设备能够稳定共享的控制内存。当前后端不再修改内核直映区，而是为同一批物理页建立单独的无缓存处理器别名。

一次分配包含四项信息：

- 分配器地址：原始可缓存直映地址，只用于最终释放页面；
- 设备地址：设备在整个生命周期中使用的地址；
- 处理器别名：单独建立的无缓存虚拟地址，也是驱动唯一可见的处理器访问地址；
- 布局：大小和对齐，用于校验及释放。

申请顺序如下：

1. 分配物理连续页面并计算设备地址；
2. 通过分配器地址清理并失效缓存；
3. 预留非空的内核虚拟地址；
4. 把原物理页以可读、可写、不可缓存属性映射到新地址；
5. 完成其他处理器核上的地址转换缓存失效和平台屏障；
6. 一次性发布处理器别名、分配器地址、设备地址和布局；
7. 通过已经发布的处理器别名把内存清零，再交给驱动。

释放顺序必须相反：

1. 驱动先确认设备已经停止访问；
2. 删除无缓存别名；
3. 完成所有处理器核的地址转换缓存失效；
4. 最后通过分配器地址释放原始页面。

删除别名期间必须继续持有地址空间锁，避免某个处理器核还保留旧转换时，同一虚拟地址已经被分配给别的对象。

处理器别名和分配器地址虽然不同，但必须指向同一批仍然存活的物理页面。`DmaAllocHandle` 因此只保留一个构造入口，要求后端同时明确给出这两个地址和设备地址；旧的双构造入口已删除。

## 7. 临时映射与中转内存

`StreamingMap` 用来临时映射调用者已有的内存。如果原地址符合设备限制，可以直接使用；否则后端申请一块满足限制的中转内存。

中转复制和缓存处理是两件独立的事：

- 只要使用中转内存，一致设备和非一致设备都必须按传输方向复制；
- 只有非一致设备需要额外执行缓存清理或失效。

这样，一致设备不会承担无意义的缓存维护，但低地址范围设备仍然能通过中转内存访问原本够不到的数据。

## 8. 页表为何仍需拆分大页

一致内存已经不再依赖“原地修改直映区属性”，但通用页表保护仍可能只修改大页中的一部分。如果不先拆分，保护 4 KiB 会影响整个 2 MiB 或 1 GiB 映射。

因此 `page-table-generic` 在保护范围跨过大页边界时，只拆分确实与边界相交的大页，并保留邻近页面的物理地址与属性。这个修复是独立的页表正确性要求，不能因为设备直接访存改用别名就删除。

龙芯架构还需要满足两项平台规则：内核动态映射区不能落入绕过页表的直映窗口；使地址转换缓存失效时要覆盖成对页面和全局内核项。否则页表已经更新，处理器仍可能继续使用旧转换。

## 9. 失败状态与回滚

建立无缓存别名是一个事务，失败点不同，能否安全回收也不同。

- 尚未安装页表项时，状态为 `NotStarted`，临时页面所有者可以正常回收页面。
- 开始安装页表项后，如果跨核失效或平台排序失败，状态为 `StateUncertain`。此时不能证明别名不可见，必须隔离虚拟地址和页面。
- 成功的非空分配只能发布非空处理器指针。数值地址零仍可用于明确的用户、客户机或设备地址，但不能作为非空处理器分配结果。
- 释放别名时如果解除映射或跨核失效失败，同样要隔离分配，不能把原始页交回分配器。

设计有意不在错误后退回普通直映地址，也不尝试原地修改直映区属性。使用哪条分配路径只能由设备的一致性属性决定，不能由一次失败临时改变。

## 10. 没有采用的方案

- 只在修改前拆分大页：能缩小影响范围，但仍然在全局直映区修改缓存属性，没有解决别名所有权问题。
- 禁用启动大页：牺牲既有启动映射设计，只是掩盖缺陷。
- 所有一致内存都通过中转缓冲区：会改变共享描述符语义，也无法解决设备和处理器需要同时观察同一内存的问题。
- 把所有设备都当成非一致：一致 PCI 设备仍会走无缓存别名分配，#1775 的失败会继续存在。
- 把所有设备都当成一致：SG2002 等设备会读取旧描述符或让处理器读取旧结果。
- 让各驱动直接调用 `somehal`：会复制方向、一致性和生命周期判断，无法统一保证正确性。
- 保留旧构造器和旧同步名称：会形成两条语义相近但约束不同的路径，调用方仍需猜测该用哪一套。

## 11. 验证要求

本设计至少需要下列确定性验证：

- 一致设备使用普通连续分配，不调用无缓存别名分配；
- 非一致设备保留不同的处理器别名和分配器地址，释放时先删除别名再释放原始页；
- 映射开始后的失败不会释放仍可能可见的页面；
- 普通复制不触发同步，所有权切换各触发一次正确方向的同步；
- 使用中转内存时，两类设备都执行复制，但只有非一致设备执行缓存维护；
- 地址范围检查覆盖最后一个字节，而不只检查起始地址；
- 队列收紧地址范围时保留原有地址空间、一致性、对齐、边界和单段长度；
- 不同地址空间或一致性属性准备的缓冲区在提交硬件前被拒绝；
- 保护大页内部一个基础页时，只改变目标页并保留邻页属性；
- RISC-V 的 NVMe 模拟机完整用例不再出现别名地址 `NoMemory`；
- SG2002 实机继续完成需要缓存处理的块设备与外设用例。

## 12. 不在本次范围内

本次改造不实现设备地址转换空间，不让一致内存分配可在硬中断中睡眠申请，也不把显式的 `prepare_for_device` / `complete_for_cpu` 所有权约定改成隐式行为。

当前 `Translated` 只是未来能力边界；只有平台真正建立并绑定了转换空间后，才能补充相应实现和验证。
