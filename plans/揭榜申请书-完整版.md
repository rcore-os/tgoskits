## 二、榜单需求理解

### 2.1 行业痛点

工业控制正向智能化、网络化演进，同一硬件平台需同时承载三类负载：

- **硬实时控制**（伺服、PWM、电机）：微秒级抖动、可度量的最坏情况响应时间；
- **智能计算**（神经网络推理）：吞吐优先、时延可容忍；
- **通用管理**（组态、日志、上位机通信）：依赖 Linux 丰富生态。

传统「多板分立」或「单 Linux + PREEMPT_RT」方案在成本、实时上限、故障隔离方面均存在明显瓶颈。基于 Type-1 Hypervisor 的**混合关键性部署**是公认演进方向，但开源方案在实时调度、标准 IP 跨域通信、AI→控制闭环方面仍缺乏可复现、可量化的完整样板。

### 2.2 榜单三大攻关任务与考核要点

| 任务 | 分值 | 核心考核 |
|---|---|---|
| 任务一：AxVisor 实时性改造与验证 | 30 分 | 调度/抢占/中断/定时器/锁的实质改造；多核 Linux 客户机；改造前后 + 空载/stress + 裸机 RTOS 对比数据 |
| 任务二：基于 IP 的客户机间通信 | 25 分 | virtio-net IP 链路（非 vsock/宿主转发）；应用层协议三类消息；可靠性/超时/重连；自动化测试与网络隔离 |
| 任务三：AI 模型与控制联动 | 25 分 | 客户机内 NN 推理；经任务二协议下发；RTOS 可观察控制动作；状态回传闭环；端到端延迟与控制效果对比 |
| 工程完整性与创新 | 20 分 | 源码 PR 合入 tgoskits dev、文档齐全、QEMU 一键复现、演示视频 |

### 2.3 本申报人对难点的理解

- **实时性**：Hypervisor vCPU 调度、虚拟中断注入、虚拟定时器是 RTOS 客户机抖动的三大不确定源；
- **通信**：跨客户机若依赖私有共享内存或宿主转发，难以审计、难以做访问控制，也不符合榜单 IP 数据面要求；
- **联动**：AI 推理（慢环）与硬实时控制（快环）架构上可解耦，但必须建立可度量的端到端下发通路与状态回传闭环。

## 四、攻关实施方案

### 4.1 总体技术路线

遵循 **「分域部署、能力下沉、通道标准化、闭环可度量」** 设计思路：

```
硬件/QEMU (aarch64, 4 pCPU)
├── pCPU0: AxVisor 管理面
├── pCPU1-2: Linux/StarryOS 客户机 (AI 推理, 2 vCPU)
└── pCPU3: RT-Thread 客户机 (实时控制, 1 vCPU 独占)

AxVisor 层：vCPU 优先级抢占 + pCPU 亲和独占 + vGIC 快速注入/直通 + 内置 virtio-net 虚拟交换
跨客户机：IP (10.0.9.0/24) + icpc 应用层协议 (UDP + ACK/重传/心跳)
闭环：Linux AI 推理 → icpc CTRL_CMD → RTOS PWM 控制 → icpc STATE_REPORT 回传
```

### 4.2 针对榜单全部难点的解决方案

#### 任务一：AxVisor 实时性（30 分）

| 改造项 | 方案 |
|---|---|
| vCPU 优先级与抢占 | RTOS vCPU 静态高优先级，就绪时 IPI 抢占低优先级 vCPU |
| pCPU 独占绑定 | RTOS vCPU pin 至 pCPU3，不参与共享域调度 |
| 中断路径 | GIC list register 快速注入；条件允许时外设中断直通 |
| 虚拟定时器 | RTOS 侧 arch timer 直访，避免 tick 陷入 |
| 锁与后台任务 | 缩短注入/调度临界区；Hypervisor 维护任务绑定共享域 pCPU |

**验证**：{改造前/后} × {空载/stress-ng} × {AxVisor RTOS/裸机 RTOS} 场景矩阵，≥30 分钟采样，输出均值/P99/P999/最大值；脚本纳入 `test-suit/axvisor/`。

#### 任务二：跨客户机 IP 通信（25 分）

- AxVisor 为双客户机各提供 virtio-net，Hypervisor 内二层虚拟交换（MAC 学习转发），数据面不经宿主；
- 静态 IP：Linux 10.0.9.2/24，RTOS 10.0.9.3/24；交换层 MAC/端口白名单实现访问控制；
- **icpc 协议**（Industrial Control Plane Communication）：`ver/type/seq/timestamp/crc32` 完整字段；支持 `CTRL_CMD`、`STATE_REPORT`、`ERROR_NOTIFY` 三类业务消息；
- UDP + 应用层可靠性（ACK、指数退避重传、去重、心跳保活）；Hypervisor 层可配置丢包/乱序注入；
- `icpc-bench` 自动化压测，输出成功率、超时率、延迟分布、有效吞吐。

#### 任务三：AI 与控制联动（25 分）

- **演示场景**：RTOS 1ms 周期 PID 控制 + 虚拟被控对象（一阶惯性+扰动）；Linux 端 ONNX Runtime 推理 MLP/1D-CNN，动态输出 PID 增益修正；
- **下发闭环**：AI 输出 → icpc `CTRL_CMD` → RTOS 调整 PWM → `STATE_REPORT` 回传；
- **延迟测量**：同侧 RTT/2 主测 + 共享 CNTVCT 辅测分段归因；
- **效果对比**：固定参数基线 vs AI 动态调参，对比稳定时间、RMSE、扰动恢复时间 ≥ 2 项指标。

### 4.3 项目创新亮点

1. **Rust Hypervisor 实时化范式**：优先级抢占 + CPU 独占 + 中断直通三位一体，TOML 配置声明实时域；
2. **Hypervisor 内生虚拟交换**：跨客户机 IP 数据面不经宿主，天然 MAC/端口级访问控制；
3. **测量先行的可复现验证体系**：全部指标固化 `cargo xtask test` 一键回归；
4. **全国产开源栈样板**：tgoskits + AxVisor + StarryOS + RT-Thread 全链路；
5. **icpc 轻量可靠控制协议**：Rust `no_std` 核心，Linux/StarryOS/RTOS 三端复用。

### 4.4 潜在风险及应对

| 风险 | 应对 |
|---|---|
| vCPU 抢占改造牵动面大 | 小步重构 + 每步 CI 回归；**pCPU 独占**作保底路线 |
| GICv2/v3 实板差异 | QEMU GICv3 先打通；直通不可用时回退快速注入 |
| RT-Thread virtio-net 适配 | 复用社区驱动；UDP 单向冒烟逐步验证 |
| 跨客户机时钟不同步 | 主用 RTT/2 测量；辅用统一 CNTVCT |
| AI 推理耗时 | 轻量 MLP 毫秒级 CPU 推理；慢环/快环架构解耦 |
| 工期延误 | 里程碑 + 每任务最小可交付版本；阶段二/三并行推进 |
