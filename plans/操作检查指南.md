# 智能化工控虚拟化项目 — 操作检查指南

本文档面向评审、复现与交卷检查，说明如何在 tgoskits 仓库中快速验证三个赛题任务的交付内容。各任务的详细设计与实现见 [`技术方案.md`](技术方案.md)、[`task1-实施记录.md`](task1-实施记录.md)、[`task2-实施记录.md`](task2-实施记录.md)、[`task3-实施记录.md`](task3-实施记录.md)；底层机制与板卡部署见 [`os/axvisor/doc/operations-guide.md`](../os/axvisor/doc/operations-guide.md)。

**测试入口约定**：除环境准备外，验收用例优先通过仓库根目录下 `scripts/task1/`、`scripts/task2/`、`scripts/task3/` 中的**可执行脚本**启动。每个脚本会自动完成客户机程序注入、镜像构建（若需要）、`cargo xtask` 测试拉起，以及报告归档；无需手工拼装多条命令。

---

## 1. 项目功能概览

本项目基于 AxVisor Type-1 Hypervisor，在 QEMU aarch64（4 pCPU）上实现「Linux 管理/AI 域 + RT 实时控制域」混合分区，并通过 VirtioNet 内网交换与 icpc 应用层协议完成跨客户机通信与控制联动。三个赛题任务与仓库主要交付物对应如下。

| 任务 | 分值 | 核心能力 | 主要代码/配置 |
| --- | ---: | --- | --- |
| 任务一 | 30 | 混合分区、vCPU 优先级、定时器直访、RT 抖动测量 | `os/axvisor/`、`virtualization/axvm/`、`test-suit/arceos/rust`（`rt-latency`） |
| 任务二 | 25 | VirtioNet + L2 虚拟交换 + icpc 协议与可靠性 | `virtualization/axvirtio-net/`、`components/icpc/`、`scripts/task2/` |
| 任务三 | 25 | AI 慢环 + RTOS PID 快环、端到端延迟与控制效果对比 | `scripts/task2/task3-ai-loop-client.c`、`scripts/task3/` |

参考拓扑：pCPU0 为 AxVisor 宿主，pCPU1–2 运行 Linux 2 vCPU 客户机，pCPU3 独占 RT 客户机。Task2/Task3 双 Linux 客户机通过 `10.0.9.0/24` 内网互通，数据面不经 vsock、IVC 或宿主 tap 转发。

## 2. 环境准备

首次复现前需安装主机工具链与 QEMU，并拉取客户机镜像。`rust-toolchain.toml` 固定 nightly 版本，首次执行 `cargo xtask` 会自动安装对应 Rust 组件。

### 2.1 主机依赖

主机需具备 `virt,virtualization=on` 的 `qemu-system-aarch64` 与 aarch64 交叉编译器。QEMU 8.0 及以上版本较稳妥；实板部署额外需要 `u-boot-tools`（`mkimage`），纯 QEMU 验收可忽略。

```bash
sudo apt install qemu-system-arm qemu-system-misc gcc-aarch64-linux-gnu
qemu-system-aarch64 --version
```

### 2.2 客户机镜像

多数用例依赖预构建 Linux 内核、Alpine rootfs 与 ArceOS 客户机镜像。在**仓库根目录**执行一次拉取即可；后续各 `run-*.sh` 脚本会引用 `tmp/axbuild/images/` 与 `tmp/axbuild/rootfs/` 下的文件。

```bash
cd /path/to/tgoskits
cargo xtask image pull qemu-aarch64 --extract-dir tmp/axbuild/images
```

若启动时报找不到 rootfs 或内核，先确认上述命令已成功，再重跑对应任务的 `run-*.sh`（脚本内会再次调用 setup 步骤）。

### 2.3 可选环境变量

长时 stress 或对比脚本会反复编译 AxVisor 与客户机，建议固定 target 目录以避免路径混乱。下列变量在脚本中已支持，可按需导出：

| 变量 | 含义 | 示例 |
| --- | --- | --- |
| `CARGO_TARGET_DIR` | Rust 编译产物目录 | `export CARGO_TARGET_DIR=$PWD/target` |
| `BOARD_IP` | RK3588 实板 SSH 地址（仅实板脚本） | `export BOARD_IP=192.168.x.x` |

## 3. 快速验收路径

若时间有限，可按下列顺序在 QEMU 上完成三任务冒烟验收。每条命令均在仓库根目录执行，预计总耗时约 **20–40 分钟**（不含首次镜像拉取与编译缓存冷启动）。

```bash
# 任务一：裸机 RT 抖动基线 + Linux 2 vCPU 冒烟
./scripts/task1/run-rt-baseline.sh
cargo xtask axvisor test qemu --arch aarch64 -c linux-smp2

# 任务二：icpc 三类消息 smoke
./scripts/task2/run-icpc-smoke.sh

# 任务三：PID 快环 + 慢环闭环
./scripts/task3/run-task3-pid-loop.sh
```

上述脚本成功结束时，串口或测试运行器输出中应分别出现 `RT_LATENCY_PASS`、`linux-smp2 pass`、`icpc-smoke pass`、`task3-pid-loop pass`（详见第 5 节判读表）。`linux-smp2` 目前仍通过 `cargo xtask` 直接调用，因其无需额外 rootfs 注入；其余任务均已封装为 `run-*.sh`。

## 4. 分任务验收脚本

以下按任务列出**推荐用于检查或交卷证据**的可执行脚本。所有路径相对于仓库根目录；脚本具有 `+x` 权限，可直接 `./scripts/...` 运行。

### 4.1 任务一 — 实时性

任务一验证混合分区下 RT 客户机周期唤醒抖动，以及改造前后对比。测量框架输出统一前缀 `RT_LATENCY`，含 `mean_jitter_ns`、`p99_jitter_ns`、`max_jitter_ns` 等字段。

| 脚本 | 用途 | 典型耗时 | 报告目录 |
| --- | --- | ---: | --- |
| `run-rt-baseline.sh` | ArceOS 裸机 RT 抖动基线（`mode=bare`） | ~5 min | 串口日志 |
| `run-rt-guest-baseline.sh` | AxVisor 单 RT 客户机 idle 短测 | ~5 min | 串口日志 |
| `collect-rt-latency-report.sh` | 裸机 vs guest idle 对比报告 | ~10 min | `plans/task1-reports/` |
| `run-stress-baseline-vs-opt-short.sh` | 混合分区 stress 短测（baseline vs opt） | ~7 min | `plans/task1-reports/` |
| `run-stress-baseline-vs-opt-long.sh` | **最佳证据**：180k 样本长稳对比 | ~70 min | `plans/task1-reports/` |
| `run-stress-strong-baseline-vs-opt-short.sh` | 强基线变体（pCPU 共核 + stress） | ~7 min | `plans/task1-reports/` |
| `run-stress-contended-baseline-vs-opt-short.sh` | RT 与 Linux 共核扰动 | ~7 min | `plans/task1-reports/` |
| `run-stress-host-share-baseline-vs-opt-short.sh` | 宿主 pCPU0 共核扰动 | ~7 min | `plans/task1-reports/` |
| `run-zephyr-rt-baseline.sh` | Zephyr RTOS 基线 smoke | ~5 min | 串口日志 |
| `run-rtthread-rt-baseline.sh` | RT-Thread 基线 smoke | ~5 min | 串口日志 |

**推荐交卷证据命令**（长稳对比，含自动 Markdown 报告）：

```bash
CARGO_TARGET_DIR=$PWD/target ./scripts/task1/run-stress-baseline-vs-opt-long.sh
```

已有报告与数据摘要见 [`task1-reports/SUBMISSION-STATUS.md`](task1-reports/SUBMISSION-STATUS.md)。

**实板（可选，需 Orange Pi 5 Plus）**：

```bash
BOARD_IP=<板子 IP> ./scripts/task1/run-board-rt-smoke.sh
CARGO_TARGET_DIR=$PWD/target ./scripts/task1/run-board-stress-baseline-vs-opt.sh
```

### 4.2 任务二 — 客户机间 IP 通信

任务二验证 VirtioNet、Hypervisor 内 L2 交换（`axvirtio-net`）与 icpc 应用层协议。各 `run-*.sh` 会先执行对应 `setup-*.sh` 将 C 客户端注入 Alpine rootfs 或 initramfs，再调用 `cargo xtask axvisor test qemu`。

| 脚本 | 对应用例 | 验证点 |
| --- | --- | --- |
| `run-virtio-net-loopback.sh` | `virtio-net-loopback` | 单 Guest eth0 回环 |
| `run-vsw-dual-guest.sh` | `vsw-dual-guest` | 双 Guest L3 互通 |
| `run-icpc-smoke.sh` | `icpc-smoke` | CTRL / ERROR / HEARTBEAT 三类消息 |
| `run-icpc-bench.sh` | `icpc-bench` | RTT、吞吐 CSV |
| `run-icpc-acl-deny.sh` | `icpc-acl-deny` | 非授权 UDP 被 ACL 拒绝 |
| `run-icpc-fault-inject.sh` | `icpc-fault-inject` | ~50% icpc 丢包下停等重试恢复 |

**推荐全量检查**（约 15–25 分钟）：

```bash
./scripts/task2/run-icpc-smoke.sh
./scripts/task2/run-icpc-bench.sh
./scripts/task2/run-icpc-acl-deny.sh
./scripts/task2/run-icpc-fault-inject.sh
```

协议库单元测试（可选）：

```bash
cargo test -p icpc
```

拓扑与地址规划见 [`task2-reports/TOPOLOGY.md`](task2-reports/TOPOLOGY.md)；交卷状态见 [`task2-reports/SUBMISSION-STATUS.md`](task2-reports/SUBMISSION-STATUS.md)。

### 4.3 任务三 — AI 与控制联动

任务三在 Task2 双 Guest 拓扑上叠加 PID 被控对象（Guest B 快环，1 ms 步进）与 Linux 慢环 AI 调参（Guest A，100 ms MLP）。`run-task3-compare.sh` 会生成 fixed vs AI 对比 Markdown 报告。

| 脚本 | 对应用例 | 验证点 |
| --- | --- | --- |
| `run-task3-pid-loop.sh` | `task3-pid-loop` | 闭环收敛，`task3-pid-loop pass` |
| `run-task3-compare.sh` | `task3-pid-compare` | RMSE、final err、p99 oneway 对比 + 报告 |

**推荐命令**：

```bash
./scripts/task3/run-task3-pid-loop.sh
./scripts/task3/run-task3-compare.sh
```

对比报告输出至 `plans/task3-reports/task3-compare-<时间戳>.md`。已有样例见 [`task3-reports/SUBMISSION-STATUS.md`](task3-reports/SUBMISSION-STATUS.md)。

## 5. 结果判读

测试运行器通过串口正则自动判定 PASS/FAIL。人工检查时，先找成功标志，再确认未出现 panic 或 `fail_regex` 命中项。双 Guest 场景下，客户机日志行可能带 `[VM n]` 前缀。

| 任务 / 用例 | 成功标志（串口或测试输出） |
| --- | --- |
| 任务一 裸机基线 | `RT_LATENCY_PASS`，且含 `RT_LATENCY mode=bare` |
| 任务一 guest / stress | `RT_LATENCY_PASS`，且含 `RT_LATENCY mode=guest` |
| 任务一 linux-smp2 | `linux-smp2 pass`（客户机 `nproc` = 2） |
| 任务二 icpc-smoke | `[VM 1] icpc-smoke pass` 或 `ICPC_CTRL_OK` 等 |
| 任务二 icpc-bench | `ICPC_BENCH_SUMMARY` |
| 任务二 icpc-fault-inject | `[VM 1] icpc-fault-inject pass`，含 `ICPC_RELIABILITY_* ok retries=` |
| 任务三 pid-loop | `task3-pid-loop pass` |
| 任务三 compare | `task3-compare pass`，以及 `TASK3_COMPARE` 指标行 |

一旦出现 `panic`、`icpc-fault-inject fail` 或 `reliability: .* failed` 等失败模式，用例判定为 FAIL，即使后续打印了部分成功字样。

## 7. 常见问题

**找不到 rootfs 或内核镜像**：未执行 `cargo xtask image pull qemu-aarch64 --extract-dir tmp/axbuild/images`，或 Task2/Task3 的 setup 未成功。重跑对应 `run-*.sh` 即可触发 setup。

**icpc 超时、无 `ICPC_*` 输出**：检查双客户机 MAC 是否与 `linux-net-a.toml` / `linux-net-b.toml` 一致；Guest B 的 peer initramfs 是否由 `setup-peer-initramfs.sh` 注入。

**fault-inject 异常**：AxVisor 须以 `vsw-fault-inject` feature 构建；请使用 `./scripts/task2/run-icpc-fault-inject.sh`，不要跳过 setup 直接跑裸 `cargo xtask`。

**编译过慢或磁盘占满**：导出 `CARGO_TARGET_DIR=$PWD/target` 并保留同一目录复用增量编译。

**开发环境问题**：见 [`开发环境问题记录.md`](开发环境问题记录.md)。
