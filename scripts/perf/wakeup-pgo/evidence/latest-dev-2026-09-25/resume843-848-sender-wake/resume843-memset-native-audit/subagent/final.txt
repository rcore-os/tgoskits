## 结论：NO-GO — 该裸 `memset` 不是可解释 ≥5us p50 缺口的 90% 候选

### 0. 核对基线（只读，未改动、未构建、未运行任何程序）

- `git rev-parse HEAD` = `69a33650763538692fafea27c869870ed0313642`（工作树干净）；提交标题 `fix(starry-kernel): keep early memset usable during PGO training`，只改了 `os/StarryOS/kernel/src/kmod/kprint.rs`（+34/-1）。

### 1. 裸 memset 本体、C ABI 与 PGO 启动约束

符号与机器码（`aarch64-linux-gnu-nm/objdump`，`resume817.elf`）：

```
ffffffff8007e2f8 0000000000000018 t memset
ffffffff8007e2f8: cbz  x2, +0x14        ; n==0 → ret
ffffffff8007e2fc: mov  x3, x0
ffffffff8007e300: strb w1, [x3], #1     ; 逐字节
ffffffff8007e304: subs x2, x2, #1
ffffffff8007e308: b.ne -8
ffffffff8007e30c: ret                   ; 返回 x0 (=s)
```

- 定义在 [kprint.rs](/home/zhourui/.codex/worktrees/03ae/tgoskits-dev/os/StarryOS/kernel/src/kmod/kprint.rs:51)（`#[cfg(all(not(target_env="musl"), target_arch="aarch64"))]` + `#[capi_fn]` + `#[unsafe(naked)]`），naked 体在 [kprint.rs:61](kprint.rs)（`cbz/mov/strb/subs/b.ne/ret`）。要求 C ABI：`x0 = s`（同时是返回值）、`w1 = c`、`x2 = n`，即 `void *memset(void *, int, size_t)`；`#[capi_fn]` 让它被全局引用，供 kmod `resolve_symbol`/kallsyms 解析。
- PGO 启动约束（resume769/774/779/783）：被 LLVM 插桩的 memset 会在 MMU 高端映射建立前访问高地址 `__llvm_prf_cnts`（resume769: `ffffffff816f4a88`，resume774: `ffffffff816deba8`），使四 crate 原生 profgen 在 before-zero marker 前挂死；naked `coverage(off)` 无关的纯汇编体抑制入口插桩，才让 profgen 镜像能启动导出计数。它是**训练可行性前提**，不是已测收益（resume779/783）。本 G 镜像（profile-use，无非空计数段）仍把全部 `memset` 引用解析到这个逐字节实现。

### 2. 测量窗口的精确定义（关键是排除 sender 的窗口外 `sched_yield`）

- 同核/跨核 futex（[handoff.c](/home/zhourui/.codex/worktrees/03ae/tgoskits-dev/apps/starry/wakeup-latency-bench/handoff.c:311)）：窗口 = sender 写 `wake_timestamp_ns` → 发布 `gate` → `FUTEX_WAKE_PRIVATE` → 调度唤醒/切换 → receiver 从 `FUTEX_WAIT` 返回后读 `resumed_ns`（[handoff.c:220](handoff.c)）。让 receiver park 的 `sched_yield()`/`nanosleep()` 在 [handoff.c:308](handoff.c)（时间戳之前），**在窗口外**。
- `bench_monotonic_ns()` 是 raw syscall `clock_gettime`（[stats.c:22-30](/home/zhourui/.codex/worktrees/03ae/tgoskits-dev/apps/starry/wakeup-latency-bench/stats.c:25)），所以窗口内还包含 receiver 侧一次 `clock_gettime` syscall。
- yield 场景（[yield.c:160-166](/home/zhourui/.codex/worktrees/03ae/tgoskits-dev/apps/starry/wakeup-latency-bench/yield.c:160)）：窗口 = sender `sched_yield` → receiver 自旋观察到 `turn` → receiver `clock_gettime`。
- timer 场景（[timer.c:26-52](/home/zhourui/.codex/worktrees/03ae/tgoskits-dev/apps/starry/wakeup-latency-bench/timer.c:26)）：窗口 = 定时器到期/ktimer 处理 → 唤醒 → 切回 sleeper → `clock_nanosleep` 返回 → `clock_gettime`。

### 4. 量级判定

该实现是逐字节循环（约 3 条指令/字节，RK3588 上大致 1–2 cycle/byte）。同核 OTHER futex 的 90% 缺口约 5186ns、跨核/timer 更大；按 ~2.4GHz 折算 5us ≈ 1.2×10⁴ cycle，需要窗口内出现大约 **≥6–12KB** 的逐字节 memset 才可能解释。测量窗口内实际 memset 量：futex/yield 同核交接 **0 字节**；timer 场景最多 **8 字节**。差距 3 个数量级。

### 5. 精确不确定项与最小证伪诊断

- 不确定项：`handle_syscall` 是一个把数百个 syscall 臂内联进同一函数的巨型函数（`0x80055e2c`–`0x8007d834`），地址相邻不等于可达。我已用两级跳表消解主要歧义——第一级 `0xffffffff80799760`（置 `w27=nr` 后跳 `0x80056a38`）、第二级 `0xffffffff80799eb8`，目标 = `0x80056a64 + int32(entry)`，解出 futex(nr=98)→`0x80056a84`、clock_gettime(nr=113)→`0x80056bdc`、sched_yield(nr=124)→`0x80056ff4`、clock_nanosleep(nr=115)→`0x80059b90`。唯一残留歧义是 `0x8006243c/800624ac`(64KB) 与 `0x8006292c/80062964`(256KB) 这 4 处 `alloc`+整块清零属于哪个臂——但它们都跟在堆分配之后，而 futex WAKE/WAIT 源码无分配、无清零，且 64KB 逐字节清零在窗口内会直接给出 ~25us 级差异（与实测 5–7us 缺口形状不符）。除此之外，窗口相关调用点长度都是常量且 ≤256B。
- 最小证伪诊断（不改变热函数代码生成）：在 `memset`（`0xffffffff8007e2f8`）挂 kprobe（内核已有 kprobe 设施）或在临时诊断镜像里让该符号自增一个 per-CPU 计数并记录最大 `x2`，跑一次冻结 full20，检查是否存在窗口内 `x2 ≥ 4096` 的调用。只要窗口内出现一次 ≥4KB 的 memset，即证伪本文结论；若最大 `x2` 始终 ≤8，则确认 memset 与 90% 缺口无关。

### 6. 决定

**NO-GO。** 该全局逐字节 `memset` 在测得的同核/跨核 futex、yield 窗口内不被调用（0 字节）；timer 场景最多 8 字节（idle 转换的 `CpuSet::clear`）；futex 实现区、`ResolvedFutex::wake`、`activate_waking_thread_locked`、`ThreadWakeBatch::wake_all` 内 memset 调用点数为 0。它作为 PGO 训练启动前提必须保留，但**不能作为 90% 性能候选**，也不应据符号存在或代码体积推断其热度。未做任何改动、构建、板测或运行验证。
