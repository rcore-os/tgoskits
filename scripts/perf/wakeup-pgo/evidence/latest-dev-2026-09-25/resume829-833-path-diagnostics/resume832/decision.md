# resume832: shared preemption transaction audit

Read-only audit at `69a33650763538692fafea27c869870ed0313642`, base `dev@05175ca38823b631a73777b0130226ddfa558439`. Findings were checked against `schedule_if_requested_owner`, rq-only schedule-out and selection publication source. No source, build, board or native performance result changed.

The common Fair same-CPU preemption path already uses one owner-rq transaction. A second rq transaction is restricted to migration/Deadline/task-lock cases and is not an extra transaction in the measured Fair futex handoff. Timer and futex paths do share some scheduling and switch work, but neither the generation-paired timer probe (`resume831`) nor prior Fair futex stage probes prove a multi-microsecond redundant operation. The reported `resume831` 6-8 us scheduler-frame-entry-to-worker-decision bucket is instrumented and includes required validation/selection. It cannot be treated as removable time. Direct wake-to-schedule candidate reuse, Fair node retention and wrapper inlining conflict with earlier negative native or source evidence in the ledger.

The full20 failure pattern is mixed: four cross-CPU futex rows have large FIFO and OTHER gaps, while OTHER same-CPU futex and yield have an additional Fair-specific gap. No single source-level shortcut is currently supported across the nine failures. A separate observation is that idle wait may restart the scheduler tick before dropping its preemption guard and the idle-to-non-idle selection tail contains a second restart call. The latter is required as a race fallback when work becomes visible after the idle checkpoint; merely deleting it would be incorrect. Its no-op cost and frequency are unmeasured and it is not a supported production candidate.

The next high-value measurement is the cross-CPU IPI receive path. Prior `resume799` timed the send call (about 1.5-1.7 us) and `resume791` noted an unmeasured global IRQ registry lock/linear lookup on receive; neither isolates receive dispatch cost. Measure the entire IPI action dispatch and its handler on the same image and board, preserving per-round count correspondence, before considering a registry change. This diagnostic cannot be counted as 90% progress. Latest valid uninstrumented full20 remains G1/G2 at 11/20, worst 58.00%.
