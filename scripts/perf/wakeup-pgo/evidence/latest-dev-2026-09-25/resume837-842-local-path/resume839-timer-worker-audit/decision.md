# resume839: OTHER timer worker path audit

The independent read-only trace is `subagent/final.txt`; I checked the central source boundaries at `runtime/service/ktimer.rs`, `runtime/cpu.rs` and `task/futex.rs` on head `69a3365076`. Fair `clock_nanosleep` uses a `ParkSoft` deadline: hard IRQ promotes due work and notifies the per-CPU `ktimers/%u` worker, which claims the generation, completes the task timer, wakes the sleeper, then parks so the receiver can run. FIFO `ParkHard` may wake directly from hard IRQ. `resume830` counted the worker's dominant entry as `PreemptExit` from idle, and `resume831` paired worker claims with scheduler stages. Those data do not reveal a duplicate worker or scheduler transaction.

Reclassifying Fair timeouts as `ParkHard` would remove the worker hop but move wake work into hard IRQ and break the intended PREEMPT_RT hard/soft split. It is not an admissible optimization. The proposed counter-only confirmation of one worker switch per claim mostly repeats valid `resume830/831` counts; it will not by itself locate the remaining Starry-vs-Linux cost. The 14 us OTHER timer threshold gap has no evidence-backed single-point fix. Shared switch/handoff cost remains a plausible contributor and should be distinguished with the separate forced-RT-preemption benchmark from `resume838`, not with another timer-only counter pass. No source, build or board state changed in this audit.
