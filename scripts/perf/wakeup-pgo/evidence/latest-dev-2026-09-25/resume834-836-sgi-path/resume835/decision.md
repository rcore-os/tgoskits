# resume835: old/current PGO provenance audit

Read-only comparison of the archived old PR `4a08610baff7cdd828f2f28d10f77d494441be09`, current packaged feature-on PGO, current weighted four-crate G, and the earlier cpufreq-off full PGO. The independent audit is in `subagent/final.txt`; the primary agent checked the build configs, wrapper, `resume756` full20 table and `resume759-frequency-scaling.md`. No source, build or board state changed.

The old 18/20 and current packaged 19/20 at Linux RT's 90% p50 threshold both enabled `ax-driver/rk3588-cpufreq`. On the current packaged feature-on image an independent PMU probe measured about 1150.266 MHz. The older 18/20 image had the same feature but **no direct frequency probe**. Both recent G1/G2 and the older cpufreq-off full-PGO `resume754/756` used the 10-feature no-cpufreq config and measured about 816 MHz in independent probes. The cpufreq-off full PGO had two valid A and two valid F full20 boots yet reached only **11/20** at 90%; worst OTHER same-CPU futex was 53.70%, and FIFO timer and thread cross-CPU futex p99.9 regressed 9.18% and 6.00% relative to same-source ordinary release. G1/G2 also reached **11/20**, worst 58.00%. `resume759` compared two valid feature-on with two valid feature-off boots: nine of ten long-case off/on p50 ratios were within 4% of the independently measured 1.4096 CPU-frequency ratio. This is strong evidence of frequency confounding, but feature, profile, source and layout also changed, so it is not a same-image causal proof.

The old `resume668` profile-use actually included `starryos`, `ax_task`, `ax_runtime` and `rsext4`; current G includes `ax_task`, `ax_sched`, `ax_runtime` and `starry_kernel`, with `starryos` excluded and a temporary exporter feature on both current A and G. The old profile had 29887 records and SHA-256 `514932b505324858df95d2bcf5cd83a5f6ae4b6c28b6135198a76acb22a0a213`; current G profile had 18127 records and SHA-256 `fcb20e25969c8eba19d0abb0ac105870b83257b6a9a3a535cd09b189e42d7b3a`. These are different training/compilation identities. Repeating an all-crate cpufreq-off PGO without a new mechanism would duplicate `resume754/756`, not produce a new candidate.

**Decision:** do not collect extra feature-on acceptance boots or promote the packaged feature-on image. Running Starry near 1150 MHz against the frozen Linux RT ~816 MHz baseline cannot establish the issue's matched-frequency 90% goal. The subagent's proposed feature-on recheck is therefore not adopted. Likewise, do not infer a code regression from old 18/20 to current 11/20. Keep the matched-frequency G1/G2 as the latest valid screen, and pursue a real runtime mechanism with source-matched 816 MHz A/B and all p50/p99/p99.9 guardrails. One useful next diagnostic is the generation-paired SGI-issue-to-CPU1-IRQ-entry stage from `resume834`; it must not be counted as a native gain.

No runtime optimization or new full20 acceptance result was produced. PR #2477 remains Draft.
