● 赛题原文、执行计划都看完了。下面是我的分析。

  结论：不是让你把它改造成 RTOS，而是做"实时虚拟化"

  赛题（《智能化工控中基于虚拟化的混合系统部署及联动实现》，见
  docs/my/openrace2026-axvisor-topics.md）的改造对象是 AxVisor 这个 
  hypervisor，不是某个内核本身。它要的是：让 RTOS 以客户机身份跑在 AxVisor
  上时，实时性不被虚拟化层毁掉；同一块硬件上还要同时跑 Linux/Starry 做 AI
  推理。这在业界叫混合关键性系统（mixed-criticality）/ 实时 hypervisor，对标
  Jailhouse、Bao、Xen 的 RTDS、PikeOS 这一类东西，而不是"再造一个 RTOS"。

  从赛题文本里可以直接读出四条证据：

  1. RTOS 已经是现成的 guest，不是交付物。 起始基线写明"已支持 RT-Thread 作为
  Guest OS"；任务一第 5 条要求选 Zephyr/RT-Thread/FreeRTOS
  做对照基线，评分点是"与原生 RTOS 基线的对比合理且可复现（5 分）"。RTOS
  在这个赛题里是尺子——用来量化"虚拟化引入了多少延迟/抖动开销"——而不是产物。
  2. 改造点全部在 hypervisor 层。
  任务一列的关键路径是"调度、抢占、定时器、中断路径、CPU
  亲和性、锁临界区、后台任务"——这些都是 AxVisor（宿主侧 ArceOS
  运行时）的机制，优化它们是为了给 guest 提供确定性的服务。
  3. 不允许把系统削成纯 RTOS。 任务一硬性要求改造后的 AxVisor 能稳定启动 ≥2 vCPU
  的多核 Linux 客户机（占 4 分）。也就是说 GPOS 和 RTOS
  必须共存，题眼是"混合部署下的隔离与确定性"，单跑一个 RTOS 反而不满足要求。
  4. 三个任务是一条工控链路。 实时性改造只占 30 分，后面还有跨客户机 IP 通信（25
  分）和"AI 推理 → 网络 → RTOS 控制 → 状态回传"闭环（25
  分）。实时底座是第一环，不是全部。

  "实时性和稳定性"在这个赛题里的确切含义

  赛题用词很精确："提升系统运行的确定性和最坏情况响应能力"。这正是实时系统理论的
  核心——衡量指标不是平均性能，而是：

  - 有界的尾延迟：p99 / p99.9 / max 中断响应延迟、调度延迟；
  - 抖动（jitter）：周期任务的周期偏差；
  - 长稳：长时间高压下不丢中断、不溢出、不 panic。

  所以"改造"意味着把 RTOS 的设计手法施加到 hypervisor
  上：定向唤醒代替广播唤醒、有界队列代替无界队列、缩小锁临界区、vCPU
  绑核隔离干扰、中断注入路径去掉不确定环节——但产物依然是一个 hypervisor。

  和你们当前工作的对应关系

  当前分支 openrace/realtime-virq-ab 的方向和赛题是对得上的：

  - vIRQ A/B 实验（notify_all + 无界 VM 队列 vs 定向 notify + 64 深度 per-vCPU
  有界队列）正是任务一"中断路径 +
  锁/队列"的实质改造，对应评分表里分值最高的一项（8 分）；有界队列 + overflow
  计数同时也是"稳定性"的直接证据。
  - 双 vCPU guest 启动（NEXT.md 3.1
  标为当前最大阻塞项）不只是实验需要——它直接对应赛题"多核 Linux
  客户机稳定启动"这条 4 分的硬性要求，值得优先打通。
  - virq_latency_stats.py 输出的 p99/p99.9/max/overrun/lost/overflow
  指标口径，和赛题第 3、4 条的测量要求一致；还缺的是赛题要求的改造前后完整 A/B 
  数据、原生 RTOS（native Zephyr）对照、空载 vs stress 对比、30 
  分钟以上长稳——这些在 plan.md 的任务一清单里也已经列出来了。

  一句话总结：赛题要的不是"把 ArceOS/AxVisor 变成 RTOS"，而是把 AxVisor 
  打造成一个能承载 RTOS 客户机、并用数据证明其确定性的实时 hypervisor，RTOS
  本身既是被服务的对象，也是衡量你做得好不好的基线。

  NEXT.md 3.1 说的"最大阻塞项"由三个根因修复解决：

  1. 20e83803a（arm_vgic）：vGIC 给每个 redistributor 都置了
  GICR_TYPER_LAST，guest 扫到第一个 GICR 帧就停止，secondary CPU 找不到自己的
  redistributor（gic_get_rdist() 返回 NULL，FAR=0x14 data
  abort）。改为只在最后一个 redistributor 置位。
  2. f837d3ad0（arm_vcpu）：这是主根因——HVC/SMC 的返回地址被重复 +4。硬件的 ELR

  返回后跳过一条 ldr x9,[sp]，随后拿着 x9=0 去 store 触发 FAR=0
  卡死。修复带了"旧实现必然失败、修复后通过"的单测。
  3. 415cc4109（axvm）：secondary vCPU 的启动屏障改回 VM 级等待队列——B 的
  per-vCPU 队列在 PSCI 启动握手完成前不安全，会死锁在 "waiting for running"。

  都能完整启动 SMP2 Zephyr guest，出现 Secondary CPU core 1 (MPID:0x1) is up 和

  但注意一个边界：标准注入场景在双 vCPU 下测不了，用了 E1 绕过

  双核启动后发现新限制（状态文档 7.4）：guest 的 k_sleep 只执行 WFI，而 HCR_EL2

  vCPU"的证据。
  - 端到端延迟 A/B 无稳定差异（park 路径延迟由唤醒/排空周期主导）。

  - 若要做"非 suspend 的标准双 vCPU 注入"，仍需 TWI trap WFI、或 injector/vCPU

  1. 最坏情况行为的改善（已有，而且是最强的一条）：E1 消融里，A 的旧路径（无条件
  wait + notify_all）在 vCPU park 场景下会把队列里的中断"搁浅"——没有人再唤醒，
  永远不会送达。用实时性的语言说，这是最坏情况延迟无穷大；改造后是有界完成（300/
  300）。"从无界/丢失到有界"正是赛题说的"最坏情况响应能力"，比 mean
  降几个百分点值钱得多。
  2. 干扰隔离的机制证据（已有）：B 对无关 vCPU 的唤醒 0 次 vs A 的 ~124
  次，且该代价随 vCPU 数按 O(N) 放大。
  3. 端到端延迟/抖动改善（还没有）——你说的就是这个缺口。

  为什么延迟上测不出来

  这不是改造没用，而是实验把信号放错了地方：

  - 信噪比太低。改动影响的是 notify/唤醒这一段（µs 级甚至 ns
  级），但测的是端到端分布——mean 约 300µs、p99 约 1ms，QEMU 平台和 host
  调度噪声主导整个分布，几 µs 的改善直接被淹没。
  - 场景没给 notify_all 制造受害者。单 vCPU 下没有别人可以被误唤醒；E1 里 vCPU0
  虽然被 A 唤醒了 124 次，但它是纯空闲的，条件 wait 把唤醒吸收在 host
  侧，代价接近零——所以延迟上看不出差别是符合预期的。
  - 全程空载。唤醒风暴和锁竞争的代价只有在系统忙碌时才显形：空载下多唤醒一个闲
  task 没人受害。
  - A 的无界队列缺陷需要突发/长时才显形。10ms/2ms 的平稳注入下队列深度基本为
  0，无界 vs 有界当然测不出差异。

  怎么把优越性"做出来"

  对着赛题评分口径（"体现最坏情况延迟或抖动改善"+"空载与 stress
  对比"）设计，而不是继续在现有场景上加轮次：

  1. 换成干扰隔离实验（受害者视角）：vCPU0 跑周期实时任务、测它的
  jitter（这本身就是赛题要求上报的指标），vCPU1 承接高频注入流。预期：A 下 vCPU0
  的 jitter 随注入频率劣化（每次注入都唤醒它的 host task），B
  下不受影响。再叠加 host 背景负载做 stress 版——受害者忙起来，124
  次/轮的虚假唤醒才有可测代价。
  2. 分段测量代替端到端：trace 已经有 enqueue→notify→ipi→running→drain
  各事件，按段统计延迟分布。B 的收益集中在 notify/唤醒段，段内分布对比能把 µs
  级差异从 ms 级平台噪声里剥出来；端到端只作为"无回归"证明。
  3. 突发 + 长稳让有界 vs 无界显形：burst 注入和 1ms 周期 10~30
  分钟长稳（NEXT.md 3.3 已有设计），量化 A 的队列增长/尾延迟拉长 vs B
  的有界背压。
  4. 把"A 搁浅中断"固化为证据：写成确定性回归测试 + 完成率/搁浅率数据，作为
  worst-case 改善的正式材料，而不是只埋在消融表里。
  5. 先修 8.4 的两个共有 bug：vGIC LR 竞态（约 1/4 轮 guest
  停摆）和定时器轮盘停驻 CNTP。不修它们长稳根本过不了；而且这两个本身就是货真价
  实的"实时性实质改造"素材——停摆 = 最坏情况无穷大，修复前后可以直接出对比数据。
  6. 记住赛题的对照轴是三方：Native RTOS / 改造前(A) / 改造后(B)。A/B
  只是其中一条边，原生 Zephyr 基线那条边同时给你"虚拟化开销有多大"的叙事。

  一句话：改造的实时性收益目前只兑现了"确定性/有界性"，还没兑现"延迟/抖动"——缺的
  不是更多轮次，而是让收益落在可测指标上的实验设计（受害者负载 + stress +
  分段测量），以及先把两个会毁掉长稳的共有 bug 修掉。

  三个候选里，真正能在"现有实验、现有工况"下压低 p99/max 的是 vGIC

  1. vGIC 注入路径 —— 能直接降当前实验的 p99.9/max ✅

  现状机制（都有代码实锤）：
  - 注入就是从 host 直写 ICH_LR：找空 LR 写 VINTID + 
  Pending（virtualization/axvm/src/arch/aarch64/gic.rs:54-90）。
  - 同 vector 已在 LR 里 Pending/Active 时 → busy →
  跳过并计数（gic.rs:59-63），调用方把边沿重入队（commit 041210b5f 修复
  #3，之前是静默丢）。
  - 全仓库没有任何 maintenance interrupt 支持：ICH_HCR_EL2 只开了 EN
  位（gic.rs:84-87），UIE/NPIE/LRENPIE 没人碰，PPI 25 没有 handler。
  - arm_vcpu 的 world switch 不保存/恢复 ICH_LR 和 AP1R（grep 全仓库，LR
  寄存器只在 gic.rs 出现）——这就是 1/4 轮"LR 停在 Active、AP1R≠0"停摆的土壤。

  为什么这是当前 p99/max 的直接来源：busy 被重入队的中断，只能等"下一次随机
  guest exit"（下一发注入 IPI，或 10ms host tick）才有机会重试。也就是说一次
  back-to-back 注入的尾延迟直接被拉到一个注入周期量级（2ms 场景里观测到的
  1.2~1.7ms max 与此吻合），停摆轮更是 max=∞。这些正是现在尾部统计里的大样本。

  具体修法（KVM 式，三步）：
  1. world switch 增加 per-vCPU 的 ICH_LR*/ICH_AP1R* 保存恢复——修停摆根因；
  2. pcpu 初始化注册 PPI 25 handler；drain 因 busy/无空 LR 而重入队时置
  ICH_HCR_EL2.NPIE（或 UIE），guest EOI 腾出 LR → maintenance IRQ → 立即 exit →
  马上补注入 → 清位。busy-defer 延迟从"最多一个周期"变成"ISR 时长 + 一次
  exit（µs 级）"；
  3. exit 时收割已 Invalid 的 LR、给仍 Active 的记账，让软件 pending 队列和 LR
  状态一致，消除 busy 误判。

  回归测试：host-test 模拟 busy 重入队后断言 NPIE
  被置位（旧实现必然失败）；实测看 lr_skip 计数、p99.9/max、停摆轮消失（这也是
  30 分钟长稳的先决条件——不修它长稳根本过不了）。

  2. 定时器单一权威 —— 降的是 guest 周期任务 jitter，不是 vIRQ 响应延迟 ⚠️

  现状机制：同一个物理比较器有三个互不知情的写入方：
